## 1. 부팅: 물리 메모리와 가상 메모리 (p.1)

```
 QEMU가 주는 물리 메모리                    가상 주소 공간 (VM)
┌──────────────┐                        ┌──────────────┐
│ pml4 (4KB)   │                        │ 커널 상 ↑      │  ← 커널이 "그대로 맺힌다"
│ 유저 풀       │ ──────────────────────▶ ├──── KERN_BASE ┤
│ 커널 풀       │                        │ 유저 프로그램 ↓ │
│ bss / 커널    │                        └──────────────┘
│ loader       │ ── paging ON ──▶ VM 활성화
└──────────────┘
      ▲ OS 디스크에서 올라옴
```

1. QEMU(에뮬레이터 = 가상 컴퓨터)가 자기 메모리를 Pintos의 물리 메모리인 것처럼 제공한다.
2. 맨 밑에 **부트 로더**가 올라가고, 로더가 OS 디스크에서 **커널 이미지**를 읽어 올린다.
3. 실행되면 **부트스트랩** 코드가 먼저 돈다. 이때 **페이징(paging)이 켜지면서 VM이 활성화**된다.
   - 필기의 "possing"은 이 **paging**이다.
4. 남은 물리 메모리는 **커널 풀**과 **유저 풀**로 나뉜다. `palloc`이 **4KB 페이지** 단위로 나눠 준다.
   - 커널 풀: 커널 자료구조, 스레드 페이지 등
   - 유저 풀: 유저 프로세스의 페이지 (`palloc_get_page(PAL_USER)`)

🎙️ "1주차 때 신경은 안 썼지만, 사실 커널 스레드들도 전부 **가상 주소**로 접근했다."

### KERN_BASE라는 선

- 가상 주소 공간에 선을 하나 긋는다: **커널 베이스 주소(`KERN_BASE`)**.
  - 이 저장소 값: `KERN_BASE = 0x8004000000` (`pintos/include/threads/vaddr.h:35`, `loader.h:9`)
- **선 위**: 커널의 상이 **그대로 맺힌다**.
- **선 아래**: 유저 프로그램이 들어간다.
- 이번 주 핵심: **새 프로세스를 만들면 그 프로세스는 별도의 VM을 할당받는다.**

### 주소 공간 크기 (퀴즈에 나왔던 것)

| | 크기 | 이유 |
|---|---|---|
| 이론상 최대 | **2⁶⁴** | 레지스터가 64비트라서. 포인터는 레지스터에 담겨야 하니 64비트를 넘으면 담을 수 없다 |
| Pintos 실제 | **2⁴⁸** | 2⁶⁴는 너무 커서 오버스펙. 하위 48비트만 쓴다 |

🎙️ "이게 사이즈가 얼마인지는 중요하지 않다. **어차피 가짜**니까."

### 프로세스마다 VM이 하나씩

- 🎙️ "프로세스 10개를 띄우면 VM이 10개, 100개 띄우면 100개가 생긴다. 이게 핵심이다."
- 그렇게 만들 수 있는 근거는? **전부 가짜(꿈, 시뮬레이션)이기 때문이다.**

### 누가 속고 있나 — CPU는 VM에 속는다

| 속이는 쪽 | 속는 쪽 | 착각 |
|---|---|---|
| QEMU | Pintos | "나는 진짜 컴퓨터 위에서 돈다" |
| **VM** | **CPU** | 🎙️ "와 시스템 쩐다, **메모리가 왜 이렇게 많아?**" |
| VM | 유저 프로그램 | (VM 주차에 자세히) |

- CPU가 다루는 주소는 **전부 가상 주소(VA)**다. 실제 물리 메모리는 수 MB~수백 MB뿐인데도 2⁴⁸ 공간이 통째로 있다고 믿는다.
- 🎙️ "VM은 **CPU를 속이기 위한 기법**이라고 생각하면 된다. 지금은 VM을 **CPU 관점**으로만 생각하자."
- 번역은 하드웨어(MMU)가 몰래 해 준다 → [5장](#5-주소-번역-pml4-4단계-페이지-테이블-p3) 참고.

## 2. 유저 프로그램의 모습: ELF (p.1)

```
 높은 주소  ┌──────────┐
           │  stack ↓ │   ← USER_STACK (0x47480000)
           │          │
           │  heap  ↑ │
           │  bss     │
           │  data    │
           │  code    │
 낮은 주소  └──────────┘
```

- "유저 프로그램이 실행된다" = 코드·데이터·BSS·힙·스택이 VM의 선 아래 영역에 **쫙 펼쳐진다**는 뜻.
- 이렇게 펼쳐질 수 있는 실행 파일 형식이 **ELF**. 유저 영역을 만들려면 **ELF를 로딩해서 펼쳐 주면** 된다.

### ELF는 어떻게 만들어지고, 뭐가 들어 있나

```
a.c ──컴파일──▶ a.o ─┐
b.c ──컴파일──▶ b.o ─┼──링킹──▶ ELF
                    ┘
```

- ELF 안에는 **가상 주소**가 들어 있다. 🎙️ "이게 핵심이다."
  - **가상 주소가 정해지는 순간 = ELF가 만들어지는 순간.** "코드는 여기, 데이터는 여기, 스택은 여기" 하고 세그먼트 위치를 이미 다 정해 둔다.
  - 리눅스 같은 시스템은 이걸 가져와서 한 번 더 가공한다. **Pintos는 그대로 쓴다.**
- Pintos는 **64비트** ELF를 쓴다. 이걸 32비트 컴퓨터에 가져가면 **안 돌아간다.**

### 크로스 컴파일

- 같은 C 코드라도 **타겟**(32비트, 64비트, 맥, 우분투…)에 따라 나오는 ELF가 **달라진다.**
- 🎙️ "C 결과물에서 가장 중요한 포인트는 **어떤 타겟에서 돌아가도록 만들어졌냐**다."
- gcc가 내가 원하는 타겟을 지원하지 않으면? 컴파일러를 직접 만들거나, 그 타겟용 컴파일러를 사야 한다.

## 3. 유저 프로그램이 시작되기까지 (녹음)

```
커널 모드                                                     유저 모드
──────────────────────────────────────────────────────────▶ ─────────────
process 초기화 → 스레드 생성 → process_exec → load(ELF) → do_iret ──▶ main()
                (1 프로세스 = 1 스레드)       (이미 있음)  (이미 있음)
```

1. 커널 모드에서 프로세스 초기화가 실행되고, **스레드를 만든다.** Pintos는 **1 프로세스 = 1 스레드**라서 스레드를 만드는 것이다.
2. `process_exec` → **`load`**가 ELF를 올린다. (`pintos/userprog/process.c:164,324`)
   - 기본으로 쓰일 프로그램 예: `pintos/tests/userprog/args.c` (args-single, args-many 등이 이걸로 돈다)
   - ELF는 **헤더 + 데이터** 형식. 헤더를 읽어서 데이터를 올린다.
   - 데이터는 **유저 풀에 4KB 단위로** 조금씩 저장한다.
   - 그 4KB마다 **가상 주소를 매기고**, 가상 주소 ↔ 물리 주소 관계를 **PML4**에 등록한다.
   - **`load`는 직접 만들 필요 없다. 이미 있다.**
   - 🎙️ "PDF든 뭐든 파일 포맷은 대부분 **헤더 + 데이터**다. ELF 로드 코드를 읽어 보면 크게 도움이 된다."
3. **`do_iret`**: 드디어 **커널 모드 → 유저 모드** 전환. (`threads/thread.c:520`, `process.c:188`)
   - 권한을 **Ring 3으로 낮추고** 선 아래로 내려와 **`main` 함수로 점프**한다.
   - 이것도 이미 만들어져 있다.
4. `main`이 유저 모드에서 돌다가, 필요한 작업이 생길 때마다 **시스템 콜**을 호출해 커널을 이용한다.

## 4. 유저 모드 ↔ 커널 모드 (p.1)

| CPL(현재 권한 레벨) | 이름 | 실행되는 코드 |
|---|---|---|
| **Ring 0** | 커널 모드 | KERN_BASE **위**의 코드 |
| **Ring 3** | 유저 모드 | KERN_BASE **아래**의 코드 |

### 커널 스레드와 유저 스레드가 따로 있어서 서로 통신하나? → **아니다**

- 🎙️ "**한 스레드**가 유저 영역에서 실행하다가, 중요한 작업이 있으면 **위(커널)로 올라간다.**"
- 중요한 작업 = 하드웨어 제어, 네트워크 사용, 스레드 생성 등.
- 올라갈 때는 **"내가 올라가서 작업하겠다"를 CPU에게 명시적으로 알려야** 한다.
  - CPU는 지금 어떤 권한으로 도는지를 **CPL 레지스터**로 안다. 이걸 **링 모드**라고 한다.

### trap = Pintos의 시스템 콜

- 유저 영역에서 실행하다가 커널로 점프하는 방식을 일반 OS 용어로 **트랩(trap)**이라고 부른다.
- **Pintos에서는 그냥 시스템 콜이라고 부른다.**
  - x86-64 `syscall` 명령 → `MSR_LSTAR`에 등록된 `syscall_entry` → `syscall_handler()`
    (`pintos/userprog/syscall.c:24,31,42`)

### 커널에서 일하려면 스택이 필요하다 → 커널 스택

- 시스템 콜로 모드가 바뀐 뒤 C 코드가 돌려면 **스택**이 필요하다.
- 그 스택은 이미 있다: **1주차에 스레드를 만들 때 커널 풀에서 받아 온 4KB 페이지**. → [6장](#6-스레드는-어디에-사나-p2)
- 🎙️ "1주차에 돌린 모든 테스트는 **커널 스택**에서 돌았다. 유저 스택에서 돌다가 시스템 콜로 올라가면 그 커널 스택에서 실행된다."
- **기본 뼈대는 있고, 시스템 콜의 내용만 빠져 있다.** 그걸 채우는 게 이번 과제다.

## 5. 주소 번역: PML4 4단계 페이지 테이블 (p.3)

> 🎙️ "오늘의 가장 어려운 부분." 어려우면 VM 주차로 미뤄도 된다고 하셨다.

### 48비트 가상 주소 쪼개기

```
 47      39 38     30 29     21 20     12 11          0
┌─────────┬─────────┬─────────┬─────────┬─────────────┐
│  PML4   │  PDPT   │   PD    │   PT    │   offset    │
│  9비트   │  9비트   │  9비트   │  9비트   │   12비트     │
└─────────┴─────────┴─────────┴─────────┴─────────────┘
   0xa       0xb       0xc       0xd      (강의 예시 인덱스)
```

- 48비트를 **9비트씩 네 번** 자르면 마지막에 **12비트**가 남는다.
- 9비트 → 각 테이블은 **2⁹ = 512칸** (인덱스 0~511).
- 한 칸(엔트리)은 **64비트(8바이트)** 포인터 → 512 × 8B = **4KB**, 테이블 하나가 페이지 하나에 딱 맞는다.
- 12비트 offset → 2¹² = **4KB**, 최종 페이지 안에서의 위치.

### 따라가는 순서 (강의 예시)

1. PML4 테이블의 `0xa` = **10번째 칸** → 다음 512칸짜리 테이블을 가리킨다
2. 그 테이블의 `0xb` = **11번째 칸** → 다음 테이블 (필기의 "0xB 11"이 이것)
3. `0xc`번 칸 → 다음 테이블
4. `0xd`번 칸 → **실제 4KB 페이지의 시작 주소**. 유저 모드 주소라면 **유저 풀**의 페이지를 가리킨다.
5. 그 페이지 시작 주소에서 **offset(12비트)**만큼 이동 → 최종 위치

- Pintos 코드: `pml4e_walk()`, `pml4_get_page()`, `pml4_set_page()` (`pintos/threads/mmu.c:65,214,233`)

### 왜 이렇게 4단계로 나누나 — 안 쓰는 건 안 만든다

- 첫 테이블 하나가 512개 테이블을, 그 각각이 또 512개를… 다 곱하면 2⁴⁸ 전체를 덮는다.
- 그런데 🎙️ "**안 쓰는 건 안 만들면 된다.** 그래서 메모리가 낭비가 안 된다. 이게 PML4 방식이다."

### PML4는 언제 채워지나

- **`load`할 때** ELF 페이지들을 올리면서 그 가상 주소를 PML4에 등록한다. (VM 주차 얘기가 아니라 지금 유저 프로그램 단계 얘기다.)

### CPU 관점: 누가 번역하나

```
VA ──▶ MMU ──▶ PA
        ├─ TLB: 한 번 쓴 주소 번역을 저장해 두는 캐시 (Pintos에도 있지만 건드릴 일 없음)
        └─ PML4를 따라가며 찾음
```

### 유저용 PML4에도 커널 영역이 들어 있다

- KERN_BASE 위(커널) 영역의 매핑은 **부팅 때** 만들어진다.
- 유저 프로그램용 PML4를 만들 때 그 커널 매핑도 **같이 포함된다.**
  - 코드: `pml4_create()`가 `base_pml4`를 통째로 복사한다 (`threads/mmu.c:96-99`)
- 🎙️ "유저 프로그램을 위해 PML4를 만들었는데, 코드를 타고 들어가 보면 커널 베이스 영역까지 같이 쓸 수 있도록 세팅된다."

### 커널은 물리 메모리와 1:1 매핑 (KVA / UVA)

```
          ┌───────────────┐
 KVA ───▶ │ 4KB (유저 풀)  │ ◀─── UVA
          └───────────────┘
 KVA = 물리주소 + KERN_BASE      UVA = 유저 프로세스의 PML4가 매핑한 주소
```

- 커널 영역은 물리 메모리를 **그대로 1:1로** 비춘다.
  - 예: 물리 주소가 `0xa`인 곳 → 커널에서는 **`0xa + KERN_BASE`**로 접근한다. (필기의 "0xa + Kernel Base Address")
  - `0x8004000000 + 0xa = 0x800400000a`
  - 위 PML4 그림의 `0xa`(인덱스 예시)와는 다른 의미다. 둘 다 그냥 예시 숫자다.
- 🎙️ "**제일 재미있는 상황**": 유저 풀에 있는 4KB 페이지 하나
  - 유저 프로세스는 **UVA**로 접근한다 → PML4가 해석하면 물리 주소가 나온다.
  - 그 물리 주소에 **KERN_BASE를 더하면** 커널이 접근할 수 있는 주소, **KVA**가 나온다.
  - **실체(물리 페이지)는 하나**, 이름(가상 주소)은 둘.
- 🎙️ "코드에서 주소에 커널 베이스를 더하는 걸 보면 '왜 더하지?' 하지 말고 '**아, 커널에서 쓰려고 하는구나**' 하고 생각하면 된다."
  - `ptov()` (물리→KVA), `vtop()` (KVA→물리) — `vaddr.h:49,53`
  - `palloc_get_page(PAL_USER)`는 **KVA**를 돌려주고, `install_page(upage, kpage, ...)`가 UVA → 그 물리 페이지를 PML4에 등록한다 (`process.c:564`).

## 6. 스레드는 어디에 사나 (p.2)

```
 커널 풀에서 받은 4KB 페이지 하나
┌──────────────────┐ ← 페이지 끝 (높은 주소)
│  커널 스택 ↓      │
│                  │
│                  │
├──────────────────┤
│  struct thread   │ ← TCB, 페이지 맨 아래에 깔림 (thread.h)
└──────────────────┘ ← 페이지 시작
```

- 스레드를 만들 때 **커널 풀에서 4KB를 끌어와**, 맨 아래에 **TCB(`struct thread`)**를 깔고 그 위를 **커널 스택**으로 쓴다.
- 스택은 위에서 아래로 자라므로, 넘치면 `struct thread`(특히 `magic`)를 덮어쓴다 → 깨지면 assertion.

## 7. 갇힌 프로세스가 바깥과 대화하는 법: 파일 추상화 (p.2)

> 🎙️ "스레드는 이 가상 메모리 박스를 쓴다. **여기서 벗어날 수 있나? 없다. 평생 여기서 산다.**"
> "그런데 외부와 통신할 일은 있다. 그래서 하나의 채널을 제공해 준다. 그게 **파일 디스크립터 테이블**이다."

(Pintos는 1 프로세스 = 1 스레드라서 강의에서는 "스레드"와 "프로세스"를 같은 뜻으로 썼다.)

### FDT(File Descriptor Table)

- 인덱스처럼 번호가 쭉 붙어 있는 표. **스레드 구조체가 같이 관리**한다.

| fd | 연결 대상 | 비고 |
|---|---|---|
| **0** | 키보드 (stdin) | 연결해 주는 함수가 이미 있다 |
| **1** | 모니터 (stdout) | **버퍼 O**: 데이터를 모았다가 부드럽게 처리. 로그 찍을 때 이걸 씀 |
| **2** | 모니터 (stderr) | **버퍼 X**: 긴급 상황용. **Pintos에서는 다루지 않는다** |
| 3 | 예: 네트워크 | 내 프로그램 → 네트워크 스택 → 라우터 → 상대 PC의 스택 |
| 4 | 예: 디스크 파일 | |
| 5 | 예: IPC (파이프) | 다른 프로세스와 통신 |

- **fd 2가 버퍼 없는 이유** 🎙️: "칼에 맞아 죽어 가는데 다행히 스택이 있어. 그런데 버퍼에 들어가면? 사라진다. 이때는 다이렉트로 '**범인은 누구다**' 하고 바로 찍을 수 있게 버퍼가 없다."
- **3번 이후**: 필기에서 3번 칸 밖으로 나가는 화살표가 이 네트워크 예시다. 스레드 입장에서는 3번이 네트워크든 4번이 파일이든 **컨트롤하는 방법에 차이를 둘 필요가 없다.**
- **IPC**: 프로세스 A와 B는 가상 메모리가 서로 달라서 직접 통신할 수 없다. 그래서 **fd를 통해 파이프로** 연결한다. (나중에 `fork` 하면서 보게 된다.)
- 📝 해석: Pintos 과제에서 3번부터는 `open`이 돌려준 **파일 객체(`struct file *`)**가 들어간다. 비어 있는 가장 작은 번호부터 배정한다.

### 왜 이름이 "파일" 디스크립터인가 — 추상화

- 🎙️ "커뮤니케이터라고 불러도 됐을 텐데 왜 파일 디스크립터라고 부를까? 이걸 이해했다면 열심히 한 거다."
- 답: **컨트롤하는 방법을 파일처럼 취급하겠다 = 파일로 추상화하겠다.**
- 🎙️ 비유: "내 앞에 벽이 있고 번호만 있다. 나는 그냥 **공을 넣고 공을 빼는 것**으로 생각한다. 내가 넣은 공이 배 타고 유럽에 갔든 옆 사람한테 갔든 나는 모른다."
- 추상화가 없으면? 블루투스 같은 장치가 새로 생길 때마다 그걸 처리하는 함수를 계속 추가해야 한다 → 힘들다.
  파일처럼 취급하면 **뭐가 추가돼도 쉽다.**
- 파일 처리는 딱 **4가지**로 추상화된다: **`open` → `read` / `write` → `close`**

### 시스템 콜과 연결하면

- 이 4가지가 결국 **시스템 콜**이고, **커널 모드에서, 커널 스택 위에서** 실행된다.
- 🎙️ "이건 제공이 안 된다. **만들어야 한다.** 하지만 **껍데기를 만드는 수준**이다."
  - FDT 자체는 없다 → 만들어야 한다.
  - 커널 안의 실제 기능(키보드 입력, 파일시스템 등)은 이미 있다 → **적절하게 호출하는 무언가**를 만들면 된다.
- 🎙️ "코드에 `open`, `read`, `write`, `close`가 딱 있다. '이게 뭐지?' 할 게 아니라, **FDT의 특정 번호로 연결하는 것**이고, 이름이 이런 건 **파일로 추상화되어 있기 때문**이라고 이해하면 쉽게 접근할 수 있다."

## 8. Project 2 해야 할 일 (p.2, p.4)

### 2-1. 인자 전달(Argument Passing) — 스택 셋업

```
명령어 한 줄:  "a -v -l2 ..."   (실행 파일 a + 옵션들 = argument)
      │
      ▼
load()         ELF 파일 가져오기            ← 이미 있음
스택 셋업       argument를 스택 맨 위에 쌓기   ← 빠져 있음, 직접 구현
      │
      ▼
유저 프로그램 실행 → write()로 출력, exit()로 종료   ← 시스템 콜 필요
```

- 필기의 `/a`는 강의에서 예로 든 **`a`라는 실행 파일**이다.

  | | 값 |
  |---|---|
  | `argv[0]` | `"a"` ← 실행할 프로그램 |
  | `argv[1]` | `"-v"` |
  | `argv[2]` | `"-l2"` |
  | … | … |
  | `argc` | 인자 개수 |

- 이 argument들이 스택이 처음 만들어질 때 **최상단에 세팅**되어야 하는데 그게 빠져 있다 → `process.c:418` TODO.
- `load()`에는 **`argv[0]`(파일 이름)만** 넘겨야 ELF를 찾는다.
- 🎙️ "이건 문서도 잘 나와 있다. **C를 잘하면 합격할 수 있는 문제**일 수도 있다."

### 왜 write와 exit가 같이 필요한가

- 🎙️ "스택을 만들어서 유저 프로그램을 돌렸는데 **로그가 안 나온다.** 왜? 출력하려면 **`write`**가 필요하니까."
  - `printf`도 결국 커널에서 출력해야 하고, **fd 1번**으로 내보내야 한다.
- 그래서 **`write`와 `exit` 정도는 만들어야 인자 전달 테스트가 통과**한다.
- 스택 셋업 + 시스템 콜 일부 + 중간중간 빠진 코드 채우기 → 🎙️ "한 번에 굉장히 많은 부분이 해결된다."

### 2-2. 파일 관련 시스템 콜

- 스펙: `create`, `remove`, 그리고 기본 `open`, `close`, `read`, `write` 등
- **FDT를 만들어야 한다.**

### 2-3. 프로세스 관리 (어드밴스드)

- 지금까지는 유저 프로그램 **하나** 안에서 다 했다. 그런데 유저 프로그램이 **또 유저 프로그램을 만드는** 상황이 있다: **`fork` / `exec` / `wait`**
- 볼 개념: 자식을 만들 때 **내 정보를 복사해 줄 것인가(fork)**, 아니면 **전체를 대체할 것인가(exec)**.
- 🎙️ "fork와 exec가 좀 어렵다. 앞의 것을 빨리 끝낸 사람은 진행하면 된다."

### 테스트 팁

- 유저 프로그램 테스트는 많지만 **대부분 엣지 케이스 검증**이다.
  - 예: 이상한 번호로 `open`, 엄청나게 큰 ELF 로드
  - 🎙️ "엣지 케이스를 충분히 고려해서 만들면 생각보다 빨리 통과될 수도 있다."
- **스레드 테스트 다시 돌리기** = **회귀 테스트**. 새로 고친 코드가 이전 기능을 망가뜨리지 않았는지 확인하는 것.
  - 🎙️ "머지한 코드가 기존 스레드 테스트를 60% 통과했는데, 돌려 보니 10%면 안 되잖아요."
- 🎙️ "진도보다 **스스로 이해하고, 시스템을 이해하고, 내 손으로 해 보는 연습**이 중요하다. AI로 학습하는 건 좋지만 코드는 본인 손으로 짜 보자."
