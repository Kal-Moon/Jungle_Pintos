## 1. 부팅: 물리 메모리와 가상 메모리 (p.1)

```
 QEMU 물리 메모리                          가상 주소 공간
┌──────────────┐                        ┌──────────────┐
│ pml4 (4KB)   │                        │   커널 영역 ↑  │
│ 유저 풀       │ ──────────────────────▶ ├──── KERN_BASE ┤
│ 커널 풀       │                        │   유저 영역 ↓  │
│ bss          │                        └──────────────┘
│ loader       │ ── passing ──▶ VM
└──────────────┘
      ▲ OS 디스크에서 올라옴
```

- 에뮬레이터(QEMU)의 물리 메모리에 **loader → 커널(bss 포함) → 커널 풀 / 유저 풀**이 자리 잡는다.
- 물리 메모리는 `palloc`이 **4KB 페이지** 단위로 나눠 주는데, 풀이 둘로 나뉜다.
  - **커널 풀**: 커널 자료구조, 스레드 페이지 등
  - **유저 풀**: 유저 프로세스의 페이지 (`palloc_get_page(PAL_USER)`)
- 가상 주소 공간은 **커널 베이스 주소(`KERN_BASE`)**를 기준으로 위는 커널, 아래는 유저.
  - 이 저장소 값: `KERN_BASE = 0x8004000000` (`pintos/include/threads/vaddr.h:35`, `loader.h:9`)
- **loader → passing → VM**: loader는 OS 디스크에서 커널을 읽어 메모리에 올린 뒤 **커널에게 제어를 넘긴다(passing)**.
  커널이 페이지 테이블(pml4)을 켜는 순간부터는 모든 주소가 가상 주소, 즉 **VM의 세계**가 된다.
  (필기에는 "possing"이라고 적혀 있다.)

### 주소 공간 크기

| | 이론상 | Pintos(x86-64) 실제 사용 |
|---|---|---|
| 가상 주소 | 2⁶⁴ | **2⁴⁸** (하위 48비트만 사용) |

### CPU는 가상 주소에 "속는다"

- CPU(정확히는 CPU에서 도는 코드)가 다루는 주소는 **전부 가상 주소(VA)**다.
- 그래서 CPU는 2⁴⁸ = 256TB짜리 넓은 공간이 통째로 있는 것처럼 **"메모리가 엄청 많다"고 착각**한다.
  실제 물리 메모리는 QEMU가 준 만큼(수 MB~수백 MB)뿐인데도 그렇다.
- 프로세스마다 이런 착각을 따로 하게 만들 수 있으니, **모든 프로세스가 자기 혼자 메모리를 다 쓴다고 믿는다.**
- 이 착각을 유지해 주는 게 VA→PA 번역이고, 하드웨어(MMU)가 몰래 해 준다 → [4장](#4-주소-번역-pml4-4단계-페이지-테이블-p3) 참고.

## 2. 유저 프로그램의 모습: ELF (p.1)

```
 높은 주소  ┌──────────┐
           │  stack ↓ │   ← USER_STACK (0x47480000)
           │          │
           │  heap  ↑ │
           │  bss     │
           │  code    │
 낮은 주소  └──────────┘
```

- 실행 파일은 **ELF** 형식이고, ELF 안에는 각 세그먼트가 놓일 **가상 주소**가 이미 적혀 있다.
- Pintos는 **64비트** ELF를 쓴다 (32비트 아님).
- 유저 프로그램은 호스트 gcc가 아니라 **크로스 컴파일**(x86-64 Pintos 대상)로 만든다.

## 3. 유저 모드 ↔ 커널 모드 (p.1)

| CPL(현재 권한 레벨) | 이름 | 누가 |
|---|---|---|
| **Ring 0** | 커널 모드 | 커널 코드, 모든 명령·메모리 접근 가능 |
| **Ring 3** | 유저 모드 | 유저 프로그램, `KERN_BASE` 위로 접근 불가 |

- 유저 영역(KERN_BASE 아래)에서 커널 영역(위)으로 넘어가는 유일한 정식 통로가 **trap**.
- Pintos에서는 이 trap이 곧 **시스템 콜**이다.
  - x86-64 `syscall` 명령 → `MSR_LSTAR`에 등록된 `syscall_entry` → `syscall_handler()`
    (`pintos/userprog/syscall.c:24,31,42`)

## 4. 주소 번역: PML4 4단계 페이지 테이블 (p.3)

### 48비트 가상 주소 쪼개기

```
 47      39 38     30 29     21 20     12 11          0
┌─────────┬─────────┬─────────┬─────────┬─────────────┐
│  PML4   │  PDPT   │   PD    │   PT    │   offset    │
│  9비트   │  9비트   │  9비트   │  9비트   │   12비트     │
└─────────┴─────────┴─────────┴─────────┴─────────────┘
   0xa       0xb       0xc       0xd      (필기 속 예시 인덱스)
```

- **9비트 × 4 + 12비트 = 48비트**.
- 9비트 → 각 테이블은 **2⁹ = 512칸** (인덱스 0~511).
- 한 칸(엔트리)은 **8바이트(64비트)** → 512 × 8B = **4KB**, 즉 테이블 하나가 페이지 하나에 딱 맞는다.
- 12비트 offset → 2¹² = **4KB**, 최종 물리 페이지 안에서의 위치.

### 따라가는 순서

1. PML4 테이블의 `[0xa]`번 칸 → 다음 테이블(PDPT)의 물리 주소
2. PDPT의 `[0xb]`번 칸 → PD
3. PD의 `[0xc]`번 칸 → PT
4. PT의 `[0xd]`번 칸 → **물리 페이지(4KB)**
5. 그 페이지 안에서 **offset**만큼 이동 → 최종 물리 주소

- Pintos 코드: `pml4e_walk()`, `pml4_get_page()`, `pml4_set_page()` (`pintos/threads/mmu.c:65,214,233`)

### 누가 번역하나

```
VA ──▶ MMU ──▶ PA
        └─ TLB (최근 번역 결과 캐시)
```

- **MMU**: 하드웨어가 위 4단계를 걸어 VA→PA로 바꾼다.
- **TLB**: 매번 4번씩 메모리를 읽으면 느리니, 최근 번역 결과를 캐시해 둔다.

### 같은 물리 페이지, 두 개의 가상 주소 (KVA / UVA)

```
          ┌───────────────┐
 KVA ───▶ │ 4KB (유저 풀)  │ ◀─── UVA
          └───────────────┘
 KVA = 물리주소 + KERN_BASE      UVA = 유저 프로세스의 pml4가 매핑한 주소
```

- 커널은 물리 메모리 전체를 **`KERN_BASE` 위에 그대로 겹쳐서** 매핑해 둔다.
  → `KVA = 물리주소 + KERN_BASE` (`ptov()` / 반대는 `vtop()`, `vaddr.h:49,53`)
- 유저 풀에서 받은 페이지 하나가
  - 커널 입장에서는 **KVA**로,
  - 유저 프로세스 입장에서는 **UVA**로 보인다. **실체(물리 페이지)는 하나.**
- 실제 코드 흐름: `palloc_get_page(PAL_USER)`가 **KVA**를 돌려주고, `install_page(upage, kpage, ...)`가 UVA → 그 물리 페이지를 pml4에 등록한다 (`process.c:564`).
- 필기의 **"0xa + Kernel Base Address"**는 예시다. 물리 주소가 `0xa`인 곳이 있다면 커널은 그곳을 `KERN_BASE + 0xa`라는 KVA로 접근한다.
  - 예: `0xa` → `0x8004000000 + 0xa = 0x800400000a`
  - 위 PML4 그림의 `0xa`(테이블 인덱스 예시)와는 다른 의미다. 둘 다 그냥 예시 숫자다.

## 5. 스레드는 어디에 사나 (p.2)

```
 커널 풀에서 받은 4KB 페이지 하나
┌──────────────────┐ ← 페이지 끝 (높은 주소)
│  커널 스택 ↓      │
│                  │
│                  │
├──────────────────┤
│  struct thread   │ ← TCB, 페이지 맨 아래에 깔림
└──────────────────┘ ← 페이지 시작
```

- 스레드를 만들 때 **커널 풀에서 4KB를 끌어와**, 맨 아래에 **TCB(`struct thread`)**를 깔고 그 위 공간을 **스택**으로 쓴다.
- 스택은 위에서 아래로 자라므로, 스택이 넘치면 `struct thread`(특히 `magic`)를 덮어쓴다 → 깨지면 assertion.

## 6. 갇힌 프로세스가 바깥과 대화하는 법: 파일 추상화 (p.2)

> **스레드(프로세스)는 자기 VM 안에 갇혀 있다. 벗어날 수는 없지만, 외부와 통신은 할 수 있다.**

그 통신 수단을 전부 **"파일"이라는 하나의 추상**으로 통일한 것이 **FDT(File Descriptor Table)**.

| fd | 대상 | 비고 |
|---|---|---|
| **0** | 키보드 (stdin) | |
| **1** | 모니터 (stdout) | **버퍼 O** |
| **2** | 모니터 (stderr) | **버퍼 X** — 긴급 상황, 1번을 못 쓸 때 |
| 3, 4, 5, … | `open`으로 연 파일들 | 각 칸이 실제 파일 객체(`struct file *`)를 가리킴 |

> 📝 해석: 필기에서 3번 칸 밖으로 나가는 화살표에는 설명이 없다. 0~2번은 장치(키보드/모니터)인 반면,
> **3번부터는 `open`이 돌려준 파일 객체를 가리킨다**는 뜻으로 해석했다. `open`은 비어 있는 가장 작은 번호(보통 3)부터 배정한다.

- 장치든 파일이든 **컨트롤하는 방법을 file로 추상화** → 인터페이스는 딱 4개면 된다:
  **`open` / `read` / `write` / `close`**
- 같은 발상의 예:
  - **네트워크**: 내 프로그램 → (네트워크) 스택 → 라우터 → 상대 PC. 이것도 소켓이라는 "파일"로 다룬다.
  - **IPC**: 다른 프로세스를 호출하는 것(프로세스 간 통신)도 결국 fd를 통한다.
- 결국 **키보드·모니터·디스크 파일·네트워크·다른 프로세스** 모두 "fd 번호 하나 + read/write"로 똑같이 다룬다.

## 7. Project 2 해야 할 일 (p.2, p.4)

### 프로그램 하나가 돌기까지

```
명령어 한 줄:  "/a -v -l2 ..."   (프로그램 이름 + 인자들)
      │
      ▼
load()         ELF 파일 가져오기       ← 이미 구현되어 있음
setup_stack()  스택 세팅(인자 쌓기)     ← 없음, 직접 구현 (2-1)
      │
      ▼
유저 프로그램 실행 → write() 로 출력, exit() 로 종료   ← 시스템 콜 필요
```

- `load`(ELF 로드)는 뼈대에 **있다**. 스택에 인자를 쌓는 부분은 **없다** → `process.c:418` TODO.
- 인자 전달이 맞았는지 테스트하려면 프로그램이 결과를 **출력(`write`)**하고 **종료(`exit`)**해야 한다.
  → 그래서 **1. 스택 세팅 → 2. 시스템 콜(`write`, `exit`)** 순서로 같이 붙여야 한다.
- 강의 예시 `/a -v -l2 ...`를 공백으로 자르면 이렇게 된다:

  | | 값 |
  |---|---|
  | `argv[0]` | `"/a"` ← 실행할 프로그램 |
  | `argv[1]` | `"-v"` |
  | `argv[2]` | `"-l2"` |
  | … | … |
  | `argc` | 인자 개수 |

  `load()`에는 **`argv[0]`(파일 이름)만** 넘겨야 ELF를 찾는다. 나머지는 유저 스택에 쌓아서 `main(argc, argv)`로 전달한다.

### 로드맵

| 단계 | 내용 | 핵심 |
|---|---|---|
| **2-1** | Argument Passing → 시스템 콜 호출 | 스택 세팅, `write`, `exit` |
| **2-2** | 파일 관련 시스템 콜 | FDT, `open`/`read`/`write`/`close` … |
| **2-3** | 프로세스 관리 | `fork` / `exec` / `wait` |
