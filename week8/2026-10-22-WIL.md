## 📚 이번 주에 배운 것

### 1. 가상 주소와 PML4 4단계 페이지 테이블

CPU가 실행 중에 내는 주소는 **전부 가상 주소(VA)** 다. 진짜 물리 주소는 CPU 위의 코드가 모른다.
번역은 하드웨어(MMU)가 몰래 해 준다.

x86-64는 이론상 64비트 주소지만, 핀토스는 **하위 48비트**만 쓴다. 이 48비트를 이렇게 쪼갠다.

```
 47      39 38     30 29     21 20     12 11          0
┌─────────┬─────────┬─────────┬─────────┬─────────────┐
│  PML4   │  PDPT   │   PD    │   PT    │   offset    │
│  9비트   │  9비트   │  9비트   │  9비트   │   12비트     │
└─────────┴─────────┴─────────┴─────────┴─────────────┘
```

- 9비트 → 테이블 하나에 **2⁹ = 512칸**
- 한 칸(엔트리)은 **8바이트** → 512 × 8B = **4KB** → 테이블 하나가 **페이지 하나에 딱 맞는다**
- 12비트 offset → 2¹² = **4KB**, 최종 물리 페이지 안에서의 위치
- 매번 4단계를 다 걸으면 느리니까 최근 번역 결과는 **TLB**에 캐시해 둔다

"왜 하필 9비트일까?"의 답은 **엔트리 512개 × 8바이트 = 4KB = 페이지 하나**라는 계산에 있었다. 테이블 하나가 정확히 페이지 하나를 차지하도록 설계된 것이다.

### 2. 같은 물리 페이지, 두 개의 가상 주소 (KVA / UVA)

```
          ┌───────────────┐
 KVA ───▶ │ 4KB (유저 풀)  │ ◀─── UVA
          └───────────────┘
 KVA = 물리주소 + KERN_BASE      UVA = 유저 프로세스의 pml4가 매핑한 주소
```

- 커널은 물리 메모리 전체를 `KERN_BASE` 위에 그대로 겹쳐서 매핑해 둔다.
- 그래서 `palloc_get_page(PAL_USER)`로 받은 페이지 하나가 **커널에게는 KVA로, 유저에게는 UVA로** 보인다. **실체는 하나.**
- `install_page(upage, kpage, ...)`가 바로 이 "UVA → 그 물리 페이지" 연결을 pml4에 등록하는 함수였다.

### 3. 유저 모드 ↔ 커널 모드, 그리고 시스템 콜

| 권한 레벨 | 이름 | 할 수 있는 것 |
|---|---|---|
| Ring 0 | 커널 모드 | 모든 명령, 모든 메모리 |
| Ring 3 | 유저 모드 | `KERN_BASE` 위로 접근 불가 |

유저가 커널에 부탁할 수 있는 유일한 정식 통로가 **시스템 콜**이다.
x86-64에서는 `int 0x80` 같은 인터럽트 대신 **`syscall` 명령어**를 쓴다.

```
유저: syscall 명령
  → MSR_LSTAR 에 등록해 둔 syscall_entry
  → syscall_handler (struct intr_frame *f)
```

레지스터 규칙도 이번에 확실히 외웠다.

| 무엇 | 레지스터 |
|---|---|
| 시스템 콜 번호 | `rax` |
| 인자 1~6 | `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9` |
| 반환값 | `rax`에 써 넣는다 (`f->R.rax`) |

그래서 핸들러는 결국 `rax`로 분기하는 `switch`문이 된다.

```c
switch (f->R.rax) {
    case SYS_HALT:
        sys_halt ();
        break;
    case SYS_EXIT:
        sys_exit ((int) f->R.rdi);
        break;
    case SYS_WRITE:
        f->R.rax = sys_write ((int) f->R.rdi, (const void *) f->R.rsi, (unsigned) f->R.rdx);
        break;
    /* ... */
    default:
        /* 모르는 번호면 유저 프로그램이 잘못 부른 것이므로 프로세스를 끝낸다. */
        sys_exit (-1);
}
```

### 4. "모든 것은 파일이다" — 파일 디스크립터 테이블

프로세스는 자기 가상 메모리에 갇혀 있지만, 바깥과 통신은 할 수 있다.
그 통신 수단을 전부 **파일이라는 하나의 추상**으로 통일한 게 FDT(File Descriptor Table)다.

| fd | 대상 |
|---|---|
| 0 | 키보드 (stdin) |
| 1 | 모니터 (stdout, 버퍼 O) |
| 2 | 모니터 (stderr, 버퍼 X) |
| 3, 4, 5 … | `open`으로 연 파일들 |

장치든 파일이든 네트워크든 `open` / `read` / `write` / `close` 네 개의 인터페이스로 다룰 수 있다는 게 인상 깊었다.

### 5. 인자 전달 (Argument Passing)

`"args-single onearg"` 같은 커맨드라인을 받아서, 유저 프로그램의 `main(argc, argv)`가 그대로 쓸 수 있도록 **유저 스택에 직접 쌓아 주는** 작업이다.
팀 `main`에는 이미 머지된 상태였지만, 원리를 확실히 이해하고 싶어서 **혼자 따로 구현**해 봤다.

순서는 이렇다.

1. `strtok_r`로 커맨드라인을 공백 기준으로 자른다
2. 문자열들을 스택 위쪽부터 **역순으로** 복사한다
3. 스택 포인터를 **8바이트 경계로 정렬**한다 (남는 칸은 0)
4. `argv[argc] = NULL`, 그다음 각 문자열의 주소(`argv[i]`)를 역순으로 쌓는다
5. `rdi = argc`, `rsi = argv 시작 주소`
6. 마지막으로 **가짜 리턴 주소(0)** 를 넣는다

`args-single onearg`를 직접 계산해 보면 스택은 이렇게 된다. (`USER_STACK = 0x47480000`)

```
주소           내용               값
0x4747fff9    "onearg\0"         (7바이트)
0x4747ffed    "args-single\0"    (12바이트)
0x4747ffe8    padding            0 (5바이트, 8의 배수 정렬)
0x4747ffe0    argv[2]            NULL
0x4747ffd8    argv[1]            0x4747fff9
0x4747ffd0    argv[0]            0x4747ffed   ← rsi
0x4747ffc8    return address     0            ← rsp

rdi = 2 (argc)
```

```c
/* 문자열을 역순으로 유저 스택에 복사하고 주소를 기억해 둔다. */
for (i = argc - 1; i >= 0; i--) {
    len = strlen (words[i]) + 1;
    if_->rsp -= len;
    memcpy ((void *) if_->rsp, words[i], len);
    arg_addrs[i] = (char *) if_->rsp;
}

/* 포인터 배열을 8바이트 경계에 맞춘다. */
zero_cnt = if_->rsp % 8;
if_->rsp -= zero_cnt;
memset ((void *) if_->rsp, 0, zero_cnt);

/* argv[argc] = NULL 부터 argv[0] 까지 역순으로 쌓는다. */
arg_addrs[argc] = NULL;
for (i = argc; i >= 0; i--) {
    if_->rsp -= 8;
    *(char **) if_->rsp = arg_addrs[i];
}

/* _start (argc, argv) 가 받도록 레지스터에 넣는다. */
if_->R.rsi = if_->rsp;
if_->R.rdi = argc;

/* 커널은 call 없이 _start 로 점프하므로 리턴 주소 자리를 0 으로 채운다. */
if_->rsp -= 8;
memset ((void *) if_->rsp, 0, 8);
```

**왜 가짜 리턴 주소를 넣을까?** 보통 함수는 `call`로 불리면서 리턴 주소가 스택에 쌓이는데,
커널은 `_start`로 그냥 점프하기 때문에 그 자리가 비어 있다. 일반적인 함수 호출과 스택 모양을 맞추려고 0을 넣는 것이다.

### 6. 유저 포인터 검증 — 유저를 믿지 마라 (내 파트)

시스템 콜 인자로 들어오는 포인터는 **유저가 마음대로 넣은 값**이다.
NULL일 수도, 커널 영역을 가리킬 수도, 매핑이 안 된 주소일 수도 있다.
커널이 그런 주소를 아무 검사 없이 읽으면 **커널 안에서 page fault**가 나서 핀토스 전체가 죽는다.

그래서 검증 함수를 3개 만들었다.

| 함수 | 검사 대상 |
|---|---|
| `validate_user_addr` | 주소 하나 |
| `validate_user_buffer` | 버퍼 전체 (시작 ~ 시작+크기-1) |
| `validate_user_string` | 문자열 (`'\0'`까지) |

```c
void
validate_user_addr (const void *uaddr) {
    /* pml4_get_page () 는 커널 주소를 넘기면 ASSERT 로 멈추므로 커널 영역 검사를 먼저 한다. */
    if (uaddr == NULL || !is_user_vaddr (uaddr)
            || pml4_get_page (thread_current ()->pml4, uaddr) == NULL)
        sys_exit (-1);
}

void
validate_user_buffer (const void *buffer, unsigned size) {
    const uint8_t *start = buffer;
    const uint8_t *end;
    const uint8_t *page;

    if (size == 0)
        return;

    /* 매핑은 페이지 단위라서, 버퍼가 걸친 페이지마다 한 번씩만 보면 된다. */
    end = start + size - 1;
    validate_user_addr (start);
    for (page = pg_round_down (start) + PGSIZE; page <= end; page += PGSIZE)
        validate_user_addr (page);
}
```

여기서 배운 포인트 두 가지.

- **검사 순서가 중요하다.** `pml4_get_page()`는 커널 주소가 들어오면 `ASSERT`로 멈춰 버린다. 그래서 `is_user_vaddr()`를 **먼저** 확인해야 한다. `||`의 단락 평가(short-circuit) 덕분에 앞에서 걸리면 뒤는 실행되지 않는다.
- **버퍼는 시작 주소만 보면 안 된다.** 버퍼가 페이지 경계에 걸쳐 있으면 앞 페이지는 매핑돼 있고 뒷 페이지는 아닐 수 있다. 매핑은 페이지 단위이므로 **버퍼가 걸친 페이지마다 한 번씩** 검사하면 된다. (바이트마다 검사할 필요는 없다!)

### 7. `page_fault`와 종료 메시지

유저 코드가 잘못된 주소를 건드린 건 **커널의 잘못이 아니라 그 프로세스의 잘못**이다.
그래서 커널을 멈추지 않고 그 프로세스만 `exit(-1)`로 끝내도록 바꿨다.

```c
/* 유저 코드에서 난 fault 면 그 프로세스만 종료 상태 -1 로 끝낸다. */
if (user)
    sys_exit (-1);
```

종료 메시지(`프로그램이름: exit(상태)`)는 테스트 채점에 그대로 쓰이기 때문에 신경 쓸 게 많았다.

```c
/* pml4 가 있는 스레드만 유저 프로세스이므로 커널 스레드는 찍지 않는다.
   process_cleanup () 이 pml4 를 지우기 전에 확인한다. */
if (curr->pml4 != NULL)
    printf ("%s: exit(%d)\n", curr->name, curr->exit_status);
```

- **출력 위치:** 정상 `exit`든 `page_fault`든 검증 실패든, 모든 종료 경로가 지나가는 `process_exit()`에서 **딱 한 번만** 찍는다.
- **커널 스레드와 `halt`는 찍지 않는다.** 유저 프로세스인지는 `pml4`가 있는지로 구분했다.
- **이름은 첫 단어만.** 스레드 이름이 커맨드라인 전체(`args-single onearg`)로 들어가고 있어서, `process_create_initd()`에서 이름용 복사본을 따로 만들어 첫 단어만 잘랐다. 원본 `fn_copy`는 `load()`가 인자 전달에 전체 커맨드라인을 써야 해서 건드리면 안 된다.

## 😵 어려웠던 점과 해결

### 1. 인자 전달 — 스택을 "거꾸로" 쌓는 감각

스택은 높은 주소에서 낮은 주소로 자라기 때문에, `argv[0]`이 가장 낮은 주소에 오게 하려면 **역순으로** 쌓아야 했다.
머릿속으로만 그리면 헷갈리기 쉬워서, 위처럼 **주소를 하나하나 직접 계산**해 보는 게 정렬(padding)이 왜 필요한지, `rsi`가 정확히 어디를 가리켜야 하는지 이해하는 데 가장 도움이 됐다.

또 하나 헷갈린 건 `strtok_r`가 **원본 문자열을 직접 고친다**(공백을 `'\0'`으로 바꾼다)는 점이었다.
내 구현에서는 `load()`의 `file_name`이 `const`라서 `palloc`으로 복사본을 하나 더 만들어 잘랐는데,
나중에 팀 코드와 비교해 보니 `load()`가 받는 문자열은 사실 `process_create_initd()`에서 이미 `palloc`으로 만든 복사본이라 그대로 잘라도 됐다.
**함수 하나만 보지 말고 호출 흐름 전체에서 메모리가 어디서 만들어지고 어디서 해제되는지 따라가야 한다**는 걸 배웠다.

### 2. 검증 함수 — "어디까지 검사해야 충분한가"

버퍼의 시작 주소만 검사하면 `*-boundary` 테스트처럼 **페이지 경계에 걸친 버퍼**를 놓치고,
반대로 바이트 하나하나 다 검사하면 낭비다.
"매핑은 페이지 단위로 된다"는 사실에서 출발하니 **페이지당 한 번**이라는 답이 자연스럽게 나왔다.
문자열은 길이를 모르니까, 한 글자씩 읽되 **새 페이지에 들어설 때만** 검사하는 방식으로 풀었다.

### 3. 커널에서 `exit(-1)` 할 때 락을 들고 있으면?

검증에 실패하면 바로 `sys_exit(-1)`로 프로세스를 끝내는데, 만약 그 순간 **파일 시스템 락을 잡고 있다면** 락이 영원히 풀리지 않아 다른 프로세스가 전부 멈춘다.
그래서 팀 규칙으로 **"유저 포인터 검증은 락 잡기 전에"** 를 정했다. `sys_write`에서도 버퍼 검증을 맨 앞에 둔 이유다.
지난주에 배운 락·세마포어가 이렇게 바로 다시 나올 줄은 몰랐다.

### 4. 협업 — 같은 파일을 셋이 동시에 고치기

`syscall.c`와 `process.c`의 `process_exit()`는 세 명이 모두 손대는 파일이었다.
충돌을 줄이기 위해

- 뼈대(필드·함수 이름·선언)를 **먼저** `main`에 올리고 각자 브랜치를 땄고,
- `process_exit()` 안에서는 **각자 블록을 나눠** 쓰고 순서(종료 메시지 → 파일 정리 → 부모 깨우기)를 미리 정했고,
- 병목이 되는 작업(종료 메시지 + `process_wait`)은 **월요일 오전 안에 머지**하기로 했다.

그런데도 문제가 생겼다. 내 작업물을 파일 업로드로 올리는 과정에서 **전날 만든 검증 함수 변경분이 빠진 채로 올라갔고**,
`struct thread`에 `exit_status` 필드와 `syscall.h` 선언이 없어서 **빌드가 깨졌다.**
빠진 변경분을 다시 적용하고 필드·선언을 추가해서 해결했지만,
"웹에서 파일 통째로 업로드"하는 방식이 얼마나 위험한지 체감했다. **변경 이력은 git으로, 작은 단위로 커밋해야 한다.**

### 5. 디버깅 `printf` 하나가 전부를 망친다

핀토스 테스트는 출력 결과를 그대로 비교해서 채점하기 때문에,
**확인용 `printf`가 하나라도 남아 있으면 모든 테스트가 FAIL**이 된다.
로직이 맞아도 출력 한 줄 때문에 전부 틀릴 수 있으니, PR 올리기 전에 디버깅 출력을 지웠는지 꼭 확인해야 한다.
