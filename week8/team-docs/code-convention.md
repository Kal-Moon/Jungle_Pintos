## 2. 모양

원래 `threads/thread.c` 와 같은 모양이다.

**함수 정의 양식**
```c
/* 한국어로 : 이 함수가 무엇을 하고, 왜 필요한가.
   부르는 쪽이 지켜야 할 조건이 있으면 적는다. (예 : 파일 시스템 락을 잡은 채로 불러야 한다) */
반환형
함수_이름 (인자_형 인자_이름, ...) {
	지역_변수_선언;

	ASSERT (지킬_조건);

	/* 본문 */
}
```

**원래 코드 예** (`thread.c` 의 `thread_unblock`)
```c
void
thread_unblock (struct thread *t) {
	enum intr_level old_level;

	ASSERT (is_thread (t));

	old_level = intr_disable ();
	...
	intr_set_level (old_level);
}
```

| ✅ 이렇게 | ❌ 이렇게 말고 | 왜 |
|---|---|---|
| `thread_yield ();` | `thread_yield();` | 원래 코드는 이름 뒤 한 칸 |
| 반환형 윗줄 · 이름 아랫줄 | `void thread_unblock (struct thread *t) {` 한 줄 | 원래 코드 모양 |
| `if (a > b) {` | `if(a>b){` | 키워드 뒤 · 연산자 양옆 한 칸 |
| 탭 들여쓰기 | 스페이스 4칸 | 섞이면 diff 전체가 바뀐다 |

- 에디터 자동 포맷은 **끈다** — 각자 끄지 않고 **저장소의 `.vscode/settings.json` 으로 맞춘다** ([7절](#7-편집기-설정))
  - 켜 두면 원래 코드 수백 줄의 모양이 바뀌어 diff 가 커진다

## 3. 이름 (snake_case)

**snake_case** = 소문자 단어를 밑줄 `_` 로 잇는다. (`exitStatus` 처럼 대문자로 잇는 camelCase 는 쓰지 않는다)

| 종류        | 규칙                               | ✅ 예                                              | ❌ 예                           |
| --------- | -------------------------------- | ------------------------------------------------ | ----------------------------- |
| 함수        | `모듈_동작` (원래처럼 파일 · 모듈 이름을 앞에)    | `process_wait` · `process_fork` · `syscall_handler` | `waitProcess` · `ProcessWait` |
| 시스템 콜 구현 함수 | `sys_` + 시스템 콜 이름 (유저 쪽 `write` · `exit` 과 이름이 겹치지 않게) | `sys_write` · `sys_open` · `sys_fork` | `write` · `my_write` · `syscallWrite` |
| 지역 변수     | 소문자 + `_`                        | `old_level` · `cur` · `child`              | `oldLevel` · `Child`     |
| 구조체 필드    | 소문자 + `_` · 무엇을 담는 값인지 이름에       | `exit_status` · `fd_table` · `running_file`   | `exitStatus` · `st` · `f2` |
| 전역 변수     | 소문자 + `_` · 파일 밖에서 안 쓰면 `static` | `static struct lock filesys_lock;`                 | `struct lock FilesysLock;`      |
| 상수 · 매크로  | 대문자 + `_`                        | `FD_MAX` · `PRI_DEFAULT`                         | `fdMax` · `fd_max`          |
| 참 / 거짓 함수 | 질문 모양 (`is_` · `has_`)           | `is_thread` · `is_user_vaddr`                          | `check_thread`                |
| 리스트 비교 함수 | `cmp_` + 기준                      | `cmp_tid`                                        | `compare1` · `my_less`        |

- 줄임말은 원래 코드에 있는 것만 (`cur` · `elem` · `fd` · `intr` · `pml4`)
- 한 글자 이름은 반복문 `i` · 원래 코드의 `t` (스레드) · `f` (`intr_frame`) 정도만
- 시스템 콜 구현 함수 · 포인터 검증 함수 · fd 찾는 함수처럼 **여러 사람이 같은 이름으로 짜야 하는 함수**는 뼈대 이슈에서 이름과 인자를 먼저 정한다 (전원이 같은 범위를 각자 짜므로, 이름이 다르면 리뷰 · 통합이 어렵다)

**구조체 필드 양식** (`include/threads/thread.h`)
```c
struct thread {
	/* Owned by thread.c. */
	tid_t tid;                          /* Thread identifier. */
	...
	int exit_status;                    /* exit 에 넘긴 종료 상태. exit · wait. */
	...
};
```
- 새 필드는 끝에 **한국어 한 줄 주석 + 어느 기능이 쓰는지** (`exit` · `wait` · `fork` · `fd` · `rox` …)
- 필드 이름 · 위치는 **뼈대 이슈에서 먼저 정한다** (셋이 같이 고치는 곳)
- 이번 과제에서만 쓰는 필드는 `#ifdef USERPROG` 안에 둔다 (원래 `pml4` 필드와 같은 위치) · `#ifdef VM` 안에는 넣지 않는다

## 4. 주석

| 규칙                              | ✅ 예                                                                                     |
| ------------------------------- | --------------------------------------------------------------------------------------- |
| `/* */` 만 쓴다 (원래 코드에 `//` 가 없다) | `/* 파일 시스템 락을 잡은 채로 불러야 한다. */`                                                             |
| 새 주석은 **한국어**                   |                                                                                         |
| 원래 영어 주석은 번역 · 삭제하지 않는다         | diff 가 커진다                                                                              |
| **무엇** 보다 **왜**                 | ❌ `/* 세마포어를 내린다. */` → ✅ `/* 자식이 복제를 끝낼 때까지 부모가 fork 에서 리턴하면 안 되므로 기다린다. */` |
| 함수 위 주석 = 하는 일 + 부르는 조건         | 2절 양식                                                                                   |
| 필드 끝 주석 = 무엇을 담는 값 + 쓰는 기능      | 3절 양식                                                                                   |

- 주석 끝에 마침표를 찍는다 (원래 코드 모양)
- 여러 줄 주석은 둘째 줄부터 `   ` (공백 3칸) 들여서 맞춘다 (원래 코드 모양)
- 주석으로 막아 둔 옛 코드는 남기지 않는다 (과제 문서 요구 · 필요하면 git 기록에서 본다)
- 원래 코드의 `/* TODO: ... */` 주석은 구현을 끝낸 뒤에도 지우지 않는다 (diff 를 줄이기 위해)

## 5. 파일 시스템 락 사용

> 주의 : `sema_up ()` 등 기존 동기화 함수에 `thread_yield ()` 를 넣지 않는다. `sema_up ()` 은 디스크 인터럽트 핸들러 안에서도 불려서, 파일 시스템을 쓰는 순간 패닉이 난다.

### 파일 시스템 락

- `filesys/` 의 함수 (`filesys_*` · `file_*`) 는 **전부 파일 시스템 락 안에서** 부른다
  - 원래 파일 시스템은 내부 동기화가 없다 (과제 문서)
  - `process_exec ()` 의 `load ()` 도 파일을 연다 — 잊지 않는다
- **락을 잡은 채로 프로세스를 종료하지 않는다**
  - 잘못된 포인터로 `exit(-1)` 하는 경로에서 특히 주의. 잡은 채 죽으면 다른 프로세스가 영원히 기다린다
- 락을 잡는 구간은 파일 시스템 호출만 감싸도록 **짧게**
- 락 이름 · 위치는 뼈대 이슈에서 하나로 정한다 (각자 다른 락을 만들면 서로를 막지 못한다)

**양식**
```c
	/* 파일 시스템은 내부 동기화가 없어서, 한 번에 한 프로세스만 들어가게 막는다. */
	lock_acquire (&filesys_lock);
	/* filesys_* · file_* 호출 */
	lock_release (&filesys_lock);
```

## 6. 상수 · 리스트 · ASSERT

| 항목 | 규칙 | 예 |
|---|---|---|
| 고정된 숫자 | 이름 붙인 상수로 (`#define`) | `#define FD_MAX 128` (fd 테이블 크기) |
| 리스트 | 원래 `lib/kernel/list.h` 함수만 쓴다 (직접 연결 고치지 않기) | `list_push_back` · `list_remove` · `list_entry` |
| 비교 함수 | `list_less_func` 모양 그대로 · 이름은 `cmp_` + 기준 | `cmp_tid` |
| `ASSERT` | 꼭 지켜야 할 조건은 `ASSERT` 로 적는다 (어기면 바로 멈춰 찾기 쉽다) | `ASSERT (fd >= 2);` |
| 유저 입력 | 유저가 넘긴 값 (포인터 · fd · 크기) 은 **`ASSERT` 로 검사하지 않는다** · 검사 함수로 걸러 `exit(-1)` 또는 에러값 | 과제 문서 : 유저 프로그램이 OS 를 멈추게 하면 안 된다 |
| 디버그 출력 | `printf` · `hex_dump` 는 **PR 전에 지운다** (테스트가 출력을 비교해서 남으면 FAIL) | |

- 여러 시스템 콜이 같이 쓰는 함수 (유저 포인터 검증 · fd 로 파일 찾기 · fd 할당) 는
  → 이름 · 인자 · 위치를 **뼈대 이슈에서 먼저 정하고**, 각자 비슷한 함수를 따로 만들지 않는다

## 7. 편집기 설정

> 셋 다 같은 개발 컨테이너에서 VS Code C/C++ 확장 (`cpptools`) 을 쓴다. 이 확장의 포맷터는 핀토스와 모양이 다르다 (스페이스 들여쓰기 · 중괄호 다음 줄).
> 한 명이라도 저장할 때 자동 포맷이 켜져 있으면 `process.c` 전체 모양이 바뀌어 PR diff 가 수백 줄이 되고, 다른 둘과 거의 확실히 충돌한다.

- 그래서 **각자 설정에 맡기지 않고** 저장소에 `.vscode/settings.json` 을 넣는다
  - 작업 영역 설정이라 **개인 설정보다 우선**한다 → 저장소를 열면 셋이 자동으로 같아진다
  - 받자마자 적용된다 (`devcontainer.json` 의 `settings` 는 컨테이너를 다시 빌드해야 적용)

**`.vscode/settings.json`**
```json
{
    "editor.formatOnSave": false,
    "editor.formatOnPaste": false,
    "editor.formatOnType": false,
    "C_Cpp.formatting": "disabled",
    "editor.insertSpaces": false,
    "editor.detectIndentation": false,
    "files.trimTrailingWhitespace": false,
    "files.insertFinalNewline": false,
    "files.eol": "\n"
}
```

| 설정 | 값 | 왜 |
|---|---|---|
| `editor.formatOnSave` · `formatOnPaste` · `formatOnType` | `false` | 저장 · 붙여넣기 · 타이핑 때 자동 포맷 끔 |
| `C_Cpp.formatting` | `"disabled"` | C/C++ 확장 포맷터 자체를 끔 (Format Document 를 눌러도 안 바뀜) |
| `editor.insertSpaces` · `editor.detectIndentation` | `false` · `false` | 탭 키가 늘 **탭** 을 넣는다 |
| `files.trimTrailingWhitespace` | `false` | 원래 코드의 줄 끝 공백을 지우면 그 줄이 바뀐 걸로 잡힌다 |
| `files.insertFinalNewline` | `false` | 파일 끝 줄바꿈을 멋대로 더하지 않는다 |
| `files.eol` | `"\n"` | 새 파일도 줄 끝 LF (리눅스 컨테이너 · 핀토스 스크립트와 같게) |

- 확인법 : 아무것도 고치지 않고 `process.c` 를 열어 저장 → `git status` 에 아무것도 안 나오면 된다

**`.gitignore`** (저장소 첫 커밋으로)
```
build/
```
- 빌드 결과물이 올라가면 diff 와 충돌이 엉망이 된다

## 8. 협업 규칙

### 8-1. 작업 나누기 : 사람별로 나누지 않고 **단계별로 전원이 같이**

- 시스템 콜을 사람별로 나누지 않는다 (코치 권고 : 전원이 전체를 이해해야 한다)
- 하루 단위 **단계**를 정하고, 그 단계 범위를 **전원이 각자 구현**한다 (팀 진행 계획 문서의 일정 · 체크리스트를 따른다)
- 저녁 리뷰에서 **기준 코드 하나**를 고르고, 다른 사람 코드의 좋은 부분은 기준 브랜치에 추가 커밋으로 옮긴다
- 모두가 같은 곳을 고치게 되므로, **공용으로 정해야 하는 것은 그날 구현 전에 뼈대 이슈에서 먼저 정한다**
  - `struct thread` 추가 필드 · 시스템 콜 구현 함수 이름 · 포인터 검증 함수 · 파일 시스템 락
  - 정해지면 한 사람이 바로 `main` 에 커밋하고, 전원이 거기서 브랜치를 딴다
- **fork · wait 는 개별 구현이 막히면 같이 앉아서 짠다** (설계는 같이, 타이핑은 한 명 · 기능마다 교대)
  - 부모 · 자식의 기다림과 해제 시점이 서로 얽혀 있어서 따로 짜서 비교하기 어렵다

### 8-2. 매일 합치기

- **하루에 한 번, 기준 코드 하나만** `main` 에 머지한다
  - 전원 브랜치를 다 머지하지 않는다 (같은 함수를 각자 짰으므로 전부 충돌한다)
  - 머지는 squash 로 해서 하루 1커밋으로 남긴다
- 다음 날은 전원이 최신 `main` 에서 새 브랜치를 딴다
- 브랜치 이름 : `feat/단계/이니셜` (단계 : `args` → `syscall-basic` → `syscall-file` → `fork-wait` → `exec` → `rox-cleanup`)
- 단계를 통과하면 `main` 에 태그를 찍는다 (예 : `day2-args-pass`) · 마지막은 `project2-final`

### 8-3. 회귀 테스트 (제일 중요)

- 핀토스는 뒤 기능이 앞 기능을 깨뜨리는 일이 흔하다
  - 예 : 포인터 검증을 넣다가 `args-*` 가 깨지고, fork 를 넣다가 `exit` 종료 메시지가 두 번 찍힌다
- 기준은 **`userprog/build` 에서 돌린 `make check`** 다 (Project 1 테스트는 여기 들어 있지 않다)
- PR 전후로 `make check` 전체를 돌린다
- **이전에 PASS 였던 테스트가 FAIL 이 되면 머지하지 않는다**
- PR 「테스트 결과」 칸에는 숫자와 함께 **새로 통과한 테스트 · 깨진 테스트 이름**을 적는다
  - 숫자만 적으면 "2개 늘고 1개 깨진" 경우를 못 잡는다

### 8-4. 리뷰 기준
