# 🍜 맛집으로 이해하는 세마포어

> 발표용 정리. 함수 이름보다 **개념**을 먼저, 비유는 **맛집** 하나로 통일한다.

## 0. 비유 규칙

| 맛집 | 세마포어 개념 |
|---|---|
| 손님 | 스레드 |
| 테이블 | 자원 |
| **빈 테이블 수** | **S** (0 이상의 정수, 음수 없음) |
| 웨이팅 명단 | 대기 큐 |
| "테이블 하나 주세요" | **P** 연산 (wait, down) |
| "테이블 하나 비었어요" | **V** 연산 (signal, up) |

> ⚠️ 비유의 한계: 테이블은 세마포어가 지키는 **자원**이지 CPU가 아니다. 스레드 상태(RUNNING/READY)는 CPU를 쓰고 있느냐의 문제로 따로 본다.

### 스레드 상태를 맛집으로: 안내 직원(CPU)은 1명

손님은 **안내 직원이 응대해 줄 때만** 무언가를 할 수 있다 (말하기, 이동하기, 식사 시작하기).

| 상태 | 맛집 | 판별: "직원이 지금 와 주면?" |
|---|---|---|
| **RUNNING** | 직원이 **지금 나를 응대 중** | — |
| **READY** | **직원 응대 줄**에 서 있음 | 바로 진행할 수 있다 |
| **BLOCKED** | **대기표 받고 잠듦** (테이블이 없음) | 와 줘도 **할 게 없다** |

- 기다림이 두 종류다: **직원을 기다리면 READY**, **테이블을 기다리면 BLOCKED**.
- 대기표 = BLOCKED. READY가 아니다.
- V로 호출받으면 테이블은 생겼지만 아직 **직원 응대를 기다리는** 상태 → READY.

---

## 1. 정의

> **세마포어 = 음이 아닌 정수 S + 대기 큐 + 두 가지 연산(P, V)**

- 1965년 다익스트라(Dijkstra)가 제안했다. 원래 뜻은 철도 **신호기**.
- 세마포어로 할 수 있는 일은 **P와 V 두 가지뿐**이다. (처음 값 정하기 제외)

---

## 2. 두 가지 연산

| 연산 | 맛집 | 확인하는 것 | 결과 |
|---|---|---|---|
| **P** | "테이블 하나 주세요" | **빈 자리 있나?** (S > 0?) | 있으면 S − 1 하고 바로 앉음<br>없으면 웨이팅 명단에 적고 잠듦 (BLOCKED) |
| **V** | "테이블 하나 비었어요" | **기다리는 사람 있나?** | 있으면 맨 앞 손님 호출 → 자리를 넘겨줌 (S 그대로)<br>없으면 S + 1 (자리가 S에 저장됨) |

### 기억할 규칙
- 대기표는 **빈 자리가 없을 때만** 받는다. P 자체가 대기표는 아니다.
- V를 하는 쪽은 **자리를 비우는 손님**이다. 기다리던 손님이 아니다.
- V를 한 쪽은 **절대 기다리지 않는다.**
- 기다리는 사람이 여러 명이어도 S는 **0에서 멈춘다.** 몇 명이 기다리는지는 웨이팅 명단이 기억한다.
- 표의 **한 줄 = 한 손님이 그 순간 도착하거나 나가는 것.** 아직 안 온 손님은 명단에 없다.
- 검산식: **앉아 있는 손님 수 + S = 전체 테이블 수**

### 예시: 테이블 2개 (S = 2)

| 순서 | 연산 | 확인 | S | 대기 | 앉아 있는 손님 |
|---|---|---|---|---|---|
| ① A 도착 | P | 빈 자리 있음 | 1 | 없음 | A |
| ② B 도착 | P | 빈 자리 있음 | 0 | 없음 | A, B |
| ③ C 도착 | P | **빈 자리 없음** | 0 | **C** | A, B |
| ④ A 식사 끝 | V | 기다리는 사람 **C** → 호출 | 0 | 없음 | B, C |
| ⑤ B 식사 끝 | V | 기다리는 사람 **없음** | **1** | 없음 | C |
| ⑥ D 도착 | P | 빈 자리 있음 (저장된 자리) | 0 | 없음 | C, D |

- ④: A가 비운 테이블은 C에게 바로 넘어간다 → S는 0 그대로.
- ⑤: 부를 사람이 없으니 빈 테이블이 S에 **저장**된다.
- ⑥: D는 누가 불러 줘서가 아니라 **자기 P로** 저장된 자리를 가져간다.

## 3. 세마포어의 성질

### ① 원자성 (Atomicity) ✅

> P와 V는 **중간에 끊기지 않고 한 덩어리로** 실행돼야 한다.

P 안에는 두 단계가 있다.
```
P = ① 빈 자리 있나 확인 (S > 0?)
    ② 있으면 하나 가져가기 (S − 1)
```

**원자적이지 않으면?** 빈 테이블 1개(S = 1), 카운터 직원 2명이 손님 X, Y를 각각 받는다.

| 순서 | 일어난 일 | S |
|---|---|---|
| 1 | X의 직원: 빈 자리 확인 → 있음! | 1 |
| 2 | Y의 직원: 빈 자리 확인 → 있음! | 1 |
| 3 | X의 직원: 하나 가져가기 | 0 |
| 4 | Y의 직원: 하나 가져가기 | **−1** |

→ 테이블 1개에 **2팀**이 앉는다. 상호 배제가 깨지고 **race condition**이 생긴다.
→ race condition을 막으려고 만든 세마포어 **안에서** race condition이 다시 생긴 것이다.
→ 컴퓨터는 혼란을 느끼거나 경고하지 않는다. **결과만 조용히 틀려진다.**

**race condition 예시: 오늘 손님 수 장부**

화이트보드에 "오늘 손님 수: 5"가 적혀 있다. 손님 두 명이 들어와 직원 두 명이 각각 1을 더한다.
더하기는 **① 보드 읽기 → ② 머릿속으로 +1 → ③ 보드에 쓰기** 세 단계다.

| 순서 | 직원 1 | 직원 2 | 보드 |
|---|---|---|---|
| 1 | ① 읽기: 5 | | 5 |
| 2 | | ① 읽기: 5 | 5 |
| 3 | ② 5 + 1 = 6 | | 5 |
| 4 | | ② 5 + 1 = 6 | 5 |
| 5 | ③ 쓰기: 6 | | 6 |
| 6 | | ③ 쓰기: 6 | **6** ❌ |

손님은 2명 왔는데 보드는 **7이 아니라 6**이다. **장부(코드)는 그대로인데 값 하나가 사라졌다.** (lost update)

**발표용 이야기 버전**

> 보드에 "오늘 손님 수: 5"가 적혀 있고, 직원 1과 직원 2 모두 이걸 봤다.
> 손님 한 명이 들어오자 직원 1은 머릿속으로 "6명"이라고 생각했지만, 보드에 적기 전에 손님을 안내하러 카운터를 비웠다.
> 그 사이 직원 2가 손님 한 명을 더 받았다. 직원 2도 머릿속으로 "6명"이라고 생각했지만, 역시 적기 전에 안내하러 갔다.
> 직원 1이 돌아와 보드에 6을 적었다.
> 직원 2도 돌아와 **보드는 보지도 않고**, 머릿속에 기억해 둔 6을 그대로 적었다.
> 손님은 2명 늘었는데 보드는 1만 늘었다.

| 이야기 속 장면 | 실제 개념 |
|---|---|
| 직원 둘 다 보드의 5를 봄 | 두 스레드가 같은 값을 **읽음** |
| 머릿속으로만 6을 알고 아직 안 적음 | 레지스터에서 **+1 계산**, 메모리에는 아직 안 씀 |
| 안내하러 카운터를 비움 | **선점 / 문맥 교환** (타이머 인터럽트로 CPU를 뺏김) |
| 그 사이 다른 직원이 같은 일을 함 | 다른 스레드가 **끼어듦** |
| 돌아와서 머릿속 값을 적음 | **쓰기** (덮어쓰기) |

> ⚠️ 사람이라면 돌아와서 보드를 다시 보고 "누가 적었나 보다" 하고 넘어갈 수 있다. 컴퓨터는 **쓰기 전에 다시 읽지 않는다.** 머릿속(레지스터) 값을 그대로 덮어쓴다. 결과는 같아 보여도 이유가 다르다.

**여러 손님이 "동시에" 오면?**
CPU는 한 순간에 스레드 하나만 실행하고, P·V는 원자적이라 **항상 한 명씩 차례로** 처리된다.

### ② 잠들어서 기다린다 (No busy waiting) ✅

| 방법 | 개념 | 맛집 |
|---|---|---|
| 바쁜 대기 (busy waiting) | 반복해서 확인하며 **CPU를 계속 씀** | 명단에 안 적고 문 앞에서 계속 "자리 났어요?" |
| 잠들어 대기 (blocking) | 대기 큐에서 잠들고 **CPU를 내놓음** | 명단에 적고 알림 올 때까지 쉬기 |

- 세마포어는 **잠들어 대기**를 쓴다. 기다리는 스레드는 BLOCKED.
- Alarm Clock에서 `timer_sleep()`의 바쁜 대기를 고친 것과 같은 원리.

**바쁜 대기 중인 스레드의 상태**

```
B: RUNNING (확인, 확인, 확인…) → 타임 슬라이스 끝 → READY → 다시 차례 → RUNNING (또 확인…)
```

- RUNNING과 READY를 **오간다.** 스스로 잠들지 않으니 **BLOCKED는 절대 안 된다.**

| | 기다리는 스레드 B의 상태 | CPU |
|---|---|---|
| 바쁜 대기 | RUNNING ↔ READY | 계속 차지하려 함 (낭비) |
| 잠들어 대기 | BLOCKED | 내놓음 → 다른 스레드가 씀 |

**바쁜 대기가 손해인 진짜 이유: 자기가 기다리는 일을 자기가 늦춘다**

- S를 1로 만드는 건 스케줄러가 아니라 **자원을 쓰던 스레드 A의 V**다.
- A가 V를 하려면 **CPU**가 필요하다.
- CPU가 1개뿐인데 B가 확인만 반복하며 CPU를 쓰면, A가 CPU를 받는 시간이 줄어든다.
- → **B가 확인을 반복할수록 A는 늦게 끝나고, S가 1이 되는 순간도 늦어진다.**
- 맛집: 문 앞 손님이 계속 "자리 났어요?" 묻느라 직원이 A의 계산을 못 해 줘서 A가 더 늦게 나간다.
- 타이머 인터럽트는 B를 강제로 내려 줘서 A가 그나마 CPU를 받게 해 준다. 이게 없으면(비선점) B가 CPU를 영원히 쥐고 A는 V를 영원히 못 한다.

**시간표로 비교: CPU 1개, 타임 슬라이스 4틱, A는 일이 4틱 남음, B가 막 RUNNING**

| 틱 | 바쁜 대기 | 잠들어 대기 |
|---|---|---|
| 0 | B: P → 자리 없음 → **확인 반복 시작** | B: P → 자리 없음 → **즉시 BLOCKED** → A가 CPU 받음 |
| 0~4 | B가 확인만 반복 (A, C는 READY에서 대기) | A가 일함 |
| 4 | 타이머가 B를 내림 → A가 CPU 받음 | **A가 V** → B 호출 |
| 4~8 | A가 일함 | |
| 8 | **A가 V** | |

→ 잠들어 대기가 **4틱 빠르다.** 바쁜 대기의 4틱은 아무 일도 안 한 시간이다.

**바쁜 대기의 피해는 스케줄링 방식에 따라 다르다**

| | 라운드 로빈 (우선순위 없음) | 우선순위 스케줄링 (B > A) |
|---|---|---|
| B의 타임 슬라이스가 끝나면 | READY 줄 **맨 뒤**로 감 | READY로 가지만 **가장 높아서 또 뽑힘** |
| 순서 | B → A → C → B → A … (차례는 돌아감) | B → B → B … (B가 독차지) |
| A | 늦어지지만 **결국 V를 함** | CPU를 **영원히 못 받음** → V 못 함 |
| 결과 | **느려짐** (B의 차례마다 시간 낭비) | **영원히 멈춤** (B는 A의 V를 기다리고, A는 B 때문에 CPU를 못 받음) |

→ 우선순위 스케줄링에서는 바쁜 대기가 "느려지는" 정도가 아니라 **진행 자체가 불가능**해진다. 기다리는 스레드를 반드시 BLOCKED로 빼야 하는 이유.

**문제 두 개, 해결책 두 개 (헷갈리지 않기)**

등장: A(20, 자원 사용 중), B(63, 같은 자원을 기다림), C(40, 상관없는 작업)

| | 문제 | 해결책 |
|---|---|---|
| ① | 기다리는 B가 **바쁜 대기**로 CPU를 독차지 → A가 V를 못 함 | **잠들어 대기** (B를 BLOCKED로) |
| ② | B는 잠들었는데, 중간 등급 **C가 A를 밀어냄** → B가 상관없는 C를 기다림 (**우선순위 역전**) | **Donation** (B가 A에게 63을 빌려줌) |

- Donation은 바쁜 대기를 해결하는 장치가 **아니다.** ①을 먼저 해결한 **다음에** 남는 ②를 해결한다.
- 기다리는 쪽이 높고(B) 자원을 쥔 쪽이 낮을 때(A)만 문제가 된다. A가 더 높으면 A가 먼저 뽑히니 문제없다.

**왜 낮은 A가 높은 B보다 먼저 자원을 가질 수 있나?**

- 우선순위는 **지금 READY인 스레드 중 누가 CPU를 쓸지**만 정한다.
- **선점은 CPU만 뺏고, 이미 가진 자원(테이블, 락)은 못 뺏는다.**
- 맛집: VIP가 와도 이미 식사 중인 일반 손님을 쫓아낼 수는 없다.

| 시점 | 일어난 일 | CPU | 테이블 |
|---|---|---|---|
| ① | B는 아직 없거나 잠들어 있음 (예: alarm). A(20)만 후보 | A | |
| ② | A가 P → 빈 테이블 있음 → 가져감 (S 1 → 0) | A | **A** |
| ③ | B(63)가 깨어나 READY → 63 > 20 → **선점** | **B** | A (쥔 채로 READY) |
| ④ | B가 P → 빈 테이블 없음 → **BLOCKED** | 비어서 다시 고름 | A |
| ⑤ | 후보: A(20), C(40) → C 실행 (역전) / 기부 있으면 A(63) 실행 | C 또는 A | A |

→ "A가 B보다 먼저 실행된다"가 아니라, **A가 B보다 먼저 와서 테이블을 잡았고, B가 그 테이블을 기다리느라 잠든 것**이다.

②의 흐름

| | 기부 없음 | 기부 있음 |
|---|---|---|
| 후보 (B는 BLOCKED) | A(20), C(40) | A(**63**), C(40) |
| 실행 | **C** → A는 C가 끝날 때까지 대기 → B도 대기 | **A** → V/해제 → B 깨어남 → B 실행 → A는 20으로 복귀 |

**맛집으로 보는 Donation, 그리고 세마포어에는 왜 없나**

- 직원(CPU)은 1명. VIP B(63)가 테이블을 기다리는데, 테이블을 쓰는 A(20)가 나가려면 직원이 계산을 해 줘야 한다.
- 직원이 C(40) 응대에 바빠서 A의 계산이 늦어지고, VIP B가 상관없는 C 때문에 기다린다. → 역전
- Donation: VIP B가 "**A 손님 계산부터 해 주세요**" → A가 VIP 대우를 빌려 먼저 나간다.
- 그런데 맛집 테이블(세마포어)은 **누가 앉았는지 기록하지 않는다.** → 누구에게 VIP 대우를 빌려줘야 할지 모른다.
- → **Donation은 소유자(holder)가 있는 락에만** 적용된다. (KAIST 문서: donation은 lock에만) → 성질 ④ "소유자가 없다"와 연결.

**A의 V는 두 경우에서 다르게 동작한다**

| | B는 웨이팅 명단에 있나? | A의 V가 하는 일 | S |
|---|---|---|---|
| 바쁜 대기 | ❌ 명단에 안 적고 문 앞에서 묻기만 함 | 부를 사람 없음 → 빈 테이블 +1 | 0 → **1** → B가 확인하고 가져감 → 0 |
| 잠들어 대기 | ✅ 명단에 있음 | B를 호출해 자리를 **바로 넘겨줌** | **0 그대로** |

- 공통점: 어느 경우든 **테이블을 비워 주는 건 A의 V**다. 스케줄러는 CPU를 누가 쓸지만 정하고, 테이블 수(S)는 건드리지 않는다.

**타이머 인터럽트 ≠ 우선순위 기부**

- 타이머 인터럽트: 시간이 다 된 스레드를 **강제로 내려 주는 장치** (선점).
- 우선순위 기부: 락을 기다리는 높은 스레드가 락 주인에게 **우선순위를 빌려주는 장치**.
- 연결점: 우선순위 스케줄링에서 높은 B가 바쁜 대기를 하면, 타이머가 B를 내려도 **가장 높은 B가 또 뽑힌다.** 낮은 A는 영원히 CPU를 못 받는다. → 그래서 기다리는 스레드는 반드시 **BLOCKED**로 빼 둬야 한다. 기부는 그다음 문제(우선순위 역전)를 푸는 장치다.

### ③ 신호를 기억한다 (Memory) — 진행 중

> V를 했는데 기다리는 손님이 없으면, 그 자리는 **S에 저장**된다. 나중에 P를 하는 손님이 **기다리지 않고** 바로 가져간다.

**포장 주문 진동벨 (S = 0으로 시작 = 신호 보내기 용도)**

- 픽업대(S)는 **빈 채로** 시작한다.
- 손님 A: 픽업대에서 P ("내 음식 주세요") → 음식을 받아서 먹는다.
- 주방 B: 요리가 끝나면 V ("음식 나왔어요") → 픽업대에 올린다.

| 경우 | 흐름 | A 상태 |
|---|---|---|
| A가 먼저 옴 | A: P → 음식 없음(S = 0) → 진동벨 들고 잠듦 → B: V → A 호출 | RUNNING → **BLOCKED** → READY → RUNNING |
| B가 먼저 끝냄 | B: V → 기다리는 손님 없음 → **픽업대에 보관 (S = 1)** → A: P → 바로 가져감 (S = 0) | **RUNNING 그대로** |

→ 어느 쪽이 먼저든 **A는 음식이 나온 뒤에만 먹는다.** P와 V의 **순서에 상관없이** 결과가 같다.
→ 신호를 기억하지 못한다면? B가 먼저 끝낸 신호가 사라져서, 나중에 온 A는 **영원히** 기다린다.

**기억하지 못하는 신호 = "외치기" 방식**

| | 외치기 방식 (기억 ❌) | 픽업대 방식 (세마포어, 기억 ✅) |
|---|---|---|
| B가 먼저 끝냄 | 아무도 없는데 "음식 나왔어요!" 외치고 끝 → **신호 사라짐** | 픽업대에 올려 둠 → **S = 1로 남음** |
| A가 나중에 와서 P | 음식 없음 → 진동벨 들고 잠듦 (BLOCKED) | 음식 있음 → 바로 가져감 (RUNNING 그대로) |
| A를 깨워 줄 사람 | **없음.** B는 이미 V를 했고 다시 하지 않는다 | 필요 없음 |
| 결과 | A는 **영원히 BLOCKED** | A는 바로 먹는다 |

- 이런 문제를 **깨움 신호 분실 (lost wakeup)** 이라고 부른다.
- "음식을 못 먹는다"보다 정확히: 음식은 **이미 나왔는데**, 그걸 알려 줄 신호가 사라져서 A가 **영원히 잠든다.**

## 학습 중 헷갈렸던 점 (발표 Q&A 대비)

- "P = 대기표, V = 대기표 반납"? → ❌ P는 **테이블 요청**, 대기표는 자리가 없을 때만. V는 **자리 반납**.
- 기다리는 순간 S는 처음 값(2)? → ❌ 다 찼으니 **0**.
- 나중에 올 손님도 대기자로 센다? → ❌ **그 줄까지 일어난 일만** 본다.
- "더하기 하나가 사라진다" = 코드가 바뀐다? → ❌ 코드는 그대로, **결과 값**이 하나 덜 늘어난다.
- 원자적이지 않으면 컴퓨터가 "혼란"을 느낀다? → ❌ 경고 없이 둘 다 들여보내고 **결과만 조용히 틀려진다.**
- 바쁜 대기 중인 스레드는 READY? RUNNING? → **둘을 오간다.** BLOCKED만 아니다.
- S를 1로 만드는 건 스케줄러/타이머 인터럽트? → ❌ **자원을 쓰던 스레드의 V.** "그 값을 실제로 바꾸는 코드를 실행하는 스레드가 누구인가"를 먼저 생각하기.
- CPU가 1개일 때, 한 스레드가 RUNNING이면 다른 스레드는 **아무것도 못 한다** (모두 READY에서 대기).
- S는 빈자리 수인데 왜 V가 S를 1로 만드나? → V = **"테이블 하나 비었어요"** = 손님이 자리를 비우는 동작. 비우는 순간 빈자리가 하나 생긴다. (단, 웨이팅 명단에 사람이 있으면 그 사람에게 바로 넘어가서 S는 그대로)
- BLOCKED는 작업이 끝나서 가는 상태? → ❌ **기다릴 게 있어서** 가는 상태. 할 일을 다 끝내면 DYING. 자리가 없는 B는 P를 하자마자 **할 일 없이 바로** BLOCKED가 된다.
- 바쁜 대기 B는 "끝날 때까지" CPU를 쓴다? → B는 끝나지 않는다(확인만 반복). **타임 슬라이스가 끝나서** 타이머가 내려 줄 때까지 쓴다.
- 바쁜 대기로 B가 CPU를 독차지하는 걸 donation으로 해결한다? → ❌ 바쁜 대기는 **BLOCKED로 재워서** 해결. donation은 그다음 문제인 **우선순위 역전**을 해결.
- 우선순위가 높은 B가 있는데 어떻게 낮은 A가 자원을 먼저 가지나? → A가 **B보다 먼저 와서** 자원을 잡았다. 선점은 CPU만 뺏고 자원은 못 뺏는다.
- P는 "작업"인가? → ❌ P는 **"테이블 주세요"라는 요청**일 뿐. 진짜 작업(식사 = 임계 구역)은 테이블을 받은 **뒤에** 한다. acquire와 P는 같은 개념(자원 하나 가져가기).
- 잠들어 대기에서 D가 자리가 났는지 계속 확인한다? → ❌ 그건 **바쁜 대기**. 잠든 D는 아무것도 안 한다. **자리를 비우는 A의 V**가 D를 깨운다.
- D가 BLOCKED가 된 이유는 "V를 받아서"? → ❌ V는 D를 **깨우는** 것. BLOCKED가 된 이유는 **빈 테이블이 없어서 기다려야 하기 때문**.

**손님 D의 하루 (잠들어 대기)**

```
D 도착 (RUNNING) → P: "테이블 주세요" → S = 0, 없음 → 대기표 받고 잠듦 (BLOCKED)
   ……  D는 아무것도 안 함  ……
A 식사 끝 → V: "테이블 비었어요" → 기다리는 D 호출 → D: BLOCKED → READY
스케줄러가 D를 고름 → D: READY → RUNNING → 앉아서 식사 (진짜 작업)
```

| 누가 | 무엇을 | D의 상태 변화 |
|---|---|---|
| D 자신 | P (요청) → 자리 없음 | RUNNING → BLOCKED |
| A | V (자리 비움) | BLOCKED → READY |
| 스케줄러 | D에게 CPU | READY → RUNNING |

- 대기표 받고 기다리는 건 READY? → ❌ **BLOCKED**. READY는 테이블이 아니라 **직원(CPU)**을 기다리는 상태.
- V로 호출받으면 바로 RUNNING? → ❌ **READY**. 직원이 응대해 줘야(스케줄러가 골라야) RUNNING.
- 깨어난 뒤 하는 일은 다시 P? → ❌ 테이블을 넘겨받았으니 **식사(진짜 작업)**.

- "Donation으로 우선순위 역전을 시킨다"? → ❌ 역전은 **문제 이름**. Donation은 역전을 **막는** 장치.
- 발표용 한 줄: **"낮은 스레드가 쥔 자원을 높은 스레드가 기다리면, 중간 스레드에게 밀려 높은 스레드가 오래 기다리는 우선순위 역전이 생길 수 있다. 이때 Donation으로 막는다. 단, 소유자가 있는 락에만 쓸 수 있다."**
- 타이머 인터럽트가 donation과 관련 있나? → ❌ 다른 장치. 타이머는 **선점**, donation은 **락 주인에게 우선순위 빌려주기**.
