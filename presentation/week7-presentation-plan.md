> - 트러블슈팅을 **"다 같이 복습"**으로 접근한다. 다른 팀도 같은 문제를 풀었으므로, 모두가 아는 함수를 맛집 웨이팅으로 다시 보는 시간으로 만든다.

> - 실제로 고치지는 못했으므로 마지막은 **FAIL 원인 분석 + 해결 방법**으로 마무리한다. ("고쳤다" ✗, "이렇게 고치면 된다" ✓)

## 슬라이드별 화면 설계

### ① 팀 구성 + 내가 고친 함수

- 윗줄: 팀 3명 / Alarm Clock: 셋이 각자 구현 → 가장 좋은 코드 채택
- 아랫줄: 내가 맡은 Priority Scheduling에서 고친 함수를 흐름으로

  ```
  Priority Scheduling
    → thread_create        새 스레드가 더 높으면 바로 양보
    → next_thread_to_run   가장 높은 스레드부터 실행 (list_max)
    → thread_set_priority  우선순위를 낮추면 더 높은 스레드에게 양보
  ```

- 근거: `thread.c`에서 실제로 바뀐 함수는 이 세 개 + 비교 함수 `compare_priority`(새로 추가). `thread_yield`는 주석만 추가됨.

### ② 테스트 결과 — 직접 만든 이미지 추천

터미널 캡처 대신 **직접 만든 결과 이미지**를 쓴다. 이유:
- 캡처에는 `priority-preempt`가 **두 번** 찍혀 있어 줄은 6줄인데 마지막 줄은 "2 of 5 tests failed"라서, 보는 사람이 숫자를 맞춰 보느라 집중이 흩어진다.
- 터미널 글씨는 발표 화면에서 작고 잘 안 보인다.

이미지 구성 (실제 테스트는 5개):

| 테스트 | 결과 | 표시 |
|---|---|---|
| priority-fifo | PASS | 기본 |
| priority-preempt | PASS | 기본 |
| priority-change | PASS | 기본 |
| **priority-sema** | **FAIL** | **빨간색 강조 + "오늘 다룰 것"** |
| priority-condvar | FAIL | 흐리게 (오늘은 다루지 않음) |

- 원본 캡처를 증거로 쓰고 싶으면 오른쪽 아래에 작게 붙인다.

### ③ 맛집 웨이팅으로 복습 (애니메이션)

1. **대응표를 화면 가운데에 크게** 띄운다.

   | 코드 | 맛집 웨이팅 |
   |---|---|
   | `value` | 빈 자리 수 |
   | `waiters` | 대기표 받고 기다리는 손님 줄 |
   | `sema_down` | 들어갈 때 |
   | `sema_up` | 나올 때 |

2. 대응표가 **오른쪽 위 구석으로 작게 이동**하고, 식당 그림이 나타난다. 식당: 입구, 테이블 2개, 대기줄 자리. (빈 자리는 숫자 대신 빈 의자로 보여 준다)
3. 손님 A가 입구로 들어오며 머리 위에 **`sema_down`** 텍스트 → 빈 테이블에 앉음.
4. 손님 B도 **`sema_down`** → 남은 테이블에 앉음. (이제 빈 자리 없음)
5. 손님 C가 **`sema_down`** → 빈 자리 없음 → **대기표 1번**을 받고 대기줄로 이동, 💤 표시 (잠듦).
6. A가 다 먹고 나가며 머리 위에 **`sema_up`** → 테이블이 빔 → "1번 손님!" 호출 → C가 💤에서 깨어나 앉음.

### ④ 헷갈리기 쉬운 점 (③ 그림 재사용)

1. ③의 장면 5(A·B 식사 중, C 대기 중)를 멈춘 그림으로 띄운다.
2. **틀린 생각** 라벨을 사람에게 붙인다: 대기 중인 C 위에 "`sema_down` = 기다리는 사람?", 나가는 A 위에 "`sema_up` = 깨우는 사람?" → 둘 다 **❌**.
3. **맞는 생각**으로 바뀜: 손님 A 한 명에게 라벨 두 개 — 들어올 때 **`sema_down`**, 나갈 때 **`sema_up`** ✅. 함수는 사람이 아니라 **한 손님이 들어갈 때/나올 때 하는 일**.
4. 보조: B가 빈 자리로 들어오는 장면에 "`sema_down`을 불러도 자리 있으면 안 기다림" 한 줄.

### ⑤ FAIL 원인과 해결 방법 (③ 그림 재사용)

1. 식당이 꽉 찬 상태에서, 손님이 한 명씩 와서 **대기표 1번 ~ 10번**을 받고 줄을 선다. **8번째로 온 손님에게만 VIP 배지** (늦게 온 VIP).

   ```
   [1] [2] [3] [4] [5] [6] [7] [8 VIP] [9] [10]
   ```

2. 손님 한 명이 나가며 **`sema_up`** → 자리가 빔.
3. **지금 코드**: 빨간 화살표가 **1번**을 가리킴, 라벨 "`list_pop_front` = 대기표 순서대로" ❌
4. **우선순위 스케줄링**: 초록 화살표가 **VIP 8번**을 가리킴 ✅
5. 아래에 해결 방법 두 줄이 나타남:
   - ① 기다리는 스레드 중 **우선순위가 가장 높은 스레드**를 깨운다
   - ② 깨운 스레드가 지금 스레드보다 높으면 **바로 양보**한다

### ⑥ 회고

- 화면에는 **"회고"** 한 단어만. 내용은 말로만.

## 대본

### ① 팀 구성 (15초)

> 저희 팀은 3명입니다. Alarm Clock은 셋이 각자 구현해서 가장 좋은 코드를 골랐고, 저는 Priority Scheduling을 맡아 thread_create, next_thread_to_run, thread_set_priority를 고쳤습니다.

### ② 테스트 결과 (12초)

> Priority Scheduling 테스트는 대부분 통과했지만, priority-sema와 priority-condvar가 실패했습니다. 오늘은 그중 priority-sema를 같이 보려고 합니다.

### ③ 맛집 웨이팅으로 복습 (31초)

> 원인을 찾다가 제가 세마포어를 제대로 모른다는 걸 알게 됐는데요, 다들 같은 문제를 푸셨으니 맛집 웨이팅으로 같이 복습해 보겠습니다. value는 빈 자리 수, waiters는 대기표를 받고 기다리는 손님 줄입니다.
>
> (애니메이션 시작) 손님이 가게에 들어갈 때 sema_down을 부릅니다. 빈 자리가 있으면 바로 앉고, 없으면 대기표를 받고 잠듭니다. 다 먹고 나올 때는 sema_up을 부릅니다. 자리를 하나 내놓고, 기다리는 손님이 있으면 호출합니다.

### ④ 헷갈리기 쉬운 점 (14초)

> 저는 sema_down은 기다리는 사람, sema_up은 깨워 주는 사람처럼 역할로 생각해서 오래 막혔습니다. 사실 둘은 한 손님이 들어갈 때와 나올 때 부르는 함수입니다. 자리가 있으면 sema_down을 불러도 기다리지 않습니다.

### ⑤ FAIL 원인과 해결 방법 (27초)

> 이제 원인이 보입니다. 지금 sema_up은 list_pop_front로 대기표 번호 순서대로 부릅니다. 그래서 1번 손님이 먼저 들어갑니다. 그런데 테스트에서는 VIP 손님이 늦게 와서 8번 대기표를 받았습니다. 우선순위 스케줄링이라면 1번이 아니라 VIP인 8번을 먼저 불러야 합니다. 그래서 고칠 점은 두 가지입니다. 첫째, 기다리는 스레드 중 우선순위가 가장 높은 스레드를 깨운다. 둘째, 깨운 스레드가 지금 스레드보다 높으면 바로 양보한다.

### ⑥ 회고 (20초)

> 공부는 그냥 재미있었습니다. 특히 계속 틀리던 이유를 파고들다가, 함수를 역할로 착각하고 있었다는 뿌리를 찾았을 때가 가장 재미있었습니다.
>
> 팀으로는 1주차와 달리 안정된 상태에서 차근차근 배울 수 있었고, 코드 리뷰를 하면서 잘하는 팀원이 문제를 어떻게 바라보는지 볼 수 있어 좋았습니다.
>
> 다음에는 무엇을 배울지, 또 얼마나 해낼 수 있을지 기대됩니다.

### 비유·시각화 규칙

- 비유는 **맛집 웨이팅 하나**로 통일. 현실에서 쓰는 말만 쓴다: 빈 자리, 대기표, 호출, 들어간다/나온다.

  | 코드 | 맛집 웨이팅 |
  |---|---|
  | `value` | 빈 자리 수 |
  | `waiters` | 대기표 받고 기다리는 손님 줄 |
  | `sema_down` | 들어갈 때: 빈 자리 있으면 바로 입장, 없으면 대기표 받고 대기 (`thread_block`) |
  | `sema_up` | 나올 때: 자리 내놓고, 기다리는 손님 있으면 호출 (`thread_unblock`) |
  | `list_pop_front` | 대기표 순서대로 호출 |
  | 우선순위 | VIP |

- 애니메이션에서 함수가 불리는 순간에는 손님 머리 위에 **함수 이름(`sema_down` / `sema_up`)을 텍스트로** 띄운다.
- 식당 그림(입구, 테이블 2개, 대기줄, 손님 모양)은 ③④⑤에서 **같은 그림을 재사용**한다.
- "직원"은 그리거나 말하지 않음. 공부 노트에서 직원은 CPU를 뜻해서 섞이면 헷갈림. 호출은 "1번 손님!"처럼 말풍선만.
- "VIP"는 ⑤에서 처음 등장 → 우선순위를 맛집 말로 바꾼 것.
- **우선순위 숫자(27, 30 등)와 `value` 숫자는 화면에 넣지 않는다.** 숫자는 대기표 번호 한 종류만. 사람들은 "1번 = 먼저 = 더 중요"라고 자연스럽게 생각하므로, 우선순위는 **VIP 배지 하나**로만 보여 준다.
- 근거(발표에서는 말하지 않음): 실제 테스트에서 스레드는 우선순위 27, 26, 25, 24, 23, 22, 21, 30, 29, 28 순서로 `sema_down`에서 줄을 섬 → 가장 높은 30이 8번째. `value`는 0에서 시작해서 모두 대기표를 받음. 질문이 나오면 이 숫자로 답한다.
- ⑤는 **"고쳤다"가 아니라 "이렇게 고치면 된다"**로 말한다.
- condvar, `cond_signal`은 ②의 결과 이미지에 FAIL로만 보이고, 설명하지 않는다.

### Q&A 대비

- **"가장 높은 스레드 깨우기"는 어떻게?** → 두 방법 중 하나. (가) `sema_up`에서 `list_max`로 가장 높은 스레드를 찾아 `list_remove` 후 깨우기 (나) `sema_down`에서 `list_insert_ordered`로 우선순위 순으로 줄 세우기. 단 (나)는 기다리는 동안 우선순위가 바뀌면(donation) 순서가 틀어지므로, `sema_up` 직전에 `list_sort`를 한 번 더 하는 경우가 많음.
- **"바로 양보"는 왜 필요?** → 테스트는 `Thread priority 30 woke up.`이 `Back in main thread.`보다 먼저 나와야 함. `thread_unblock`은 ready_list에 넣기만 하므로, `sema_up` 끝에서 깨운 스레드가 더 높으면 `thread_yield`를 해야 함.
- **priority-condvar는요?** → "condition variable은 아직 개념을 따로 공부해야 해서 이번 발표에서는 뺐습니다."
- **VIP가 이미 먹고 있는 손님을 쫓아낼 수 있나?** → 아니요. 우선순위는 READY 스레드 중 누가 CPU를 쓸지만 정함. 자리(자원)는 뺏지 못함.

## FAIL 원인 확인 (코드 기준, 실행은 못 함)

이 환경에 qemu가 없어 테스트를 직접 돌리지는 못했고, 코드와 테스트 기대 출력을 대조해 확인함. 발표에서는 "원인"으로 말해도 됨.

1. **V(`sema_up`)가 웨이팅 명단 맨 앞을 깨운다 → 확인됨**
   - `pintos/threads/synch.c:69` `sema_down`: `list_push_back`으로 명단 **뒤에** 추가 (온 순서대로 줄 섬)
   - `pintos/threads/synch.c:113` `sema_up`: `list_pop_front`로 명단 **맨 앞**을 깨움 (우선순위 무시)
   - `priority-sema` 테스트: main이 `PRI_MIN`으로 내려간 뒤 우선순위 27, 26, 25, 24, 23, 22, 21, 30, 29, 28 순서로 스레드를 만듦. 각 스레드가 바로 선점해 `sema_down`에서 줄을 서므로 명단 순서도 같음 → 현재 코드는 **27**을 먼저 깨우지만 기대 출력은 **30**부터.
2. **깨운 뒤 양보하지 않는다 → 함께 고쳐야 할 점**
   - 기대 출력은 `Thread priority 30 woke up.` 다음에 `Back in main thread.`가 나와야 함. 즉 깨어난 스레드(30)가 main(`PRI_MIN`)보다 먼저 실행돼야 함.
   - 지금 `thread_unblock`은 ready_list에 넣기만 하고, `sema_up`도 양보(`thread_yield`)를 하지 않음 → main이 계속 실행되어 `Back in main thread.`가 먼저 찍힘.
3. **condvar도 같은 원리 → 코드로 확인됨 (발표에서는 제외, 따로 공부 예정)**
   - `pintos/threads/synch.c:306` `cond_signal`도 `cond->waiters`에서 `list_pop_front`로 맨 앞을 깨움.
   - 차이: condvar의 명단 원소는 스레드가 아니라 `semaphore_elem`(각자 세마포어 하나씩)이라, 정렬할 때 "그 세마포어에서 기다리는 스레드의 우선순위"를 비교해야 함.
