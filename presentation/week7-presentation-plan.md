## 흐름 (슬라이드 7장, 약 2분)

> 이야기 줄기: **priority-sema FAIL → 원인을 보다가 세마포어 자체를 몰랐다는 걸 알게 됨 → 맛집 웨이팅으로 공부 → 웨이팅으로 보니 원인과 고칠 방법이 보임**
>
> 핵심 전략
> - 트러블슈팅을 **"다 같이 복습"**으로 접근한다. 다른 팀도 같은 문제를 풀었으므로, 모두가 아는 함수를 맛집 웨이팅으로 다시 보는 시간으로 만든다.
> - 용어는 P/V가 아니라 **`sema_down` / `sema_up` 함수 이름**으로 말한다.
> - 비유는 누구나 해 본 **맛집 웨이팅 (대기표 + 순서대로 호출)**. "테이블 주세요" 같은 현실에서 안 쓰는 말은 쓰지 않는다.
> - **condition variable(`cond_signal`, condvar)은 다루지 않는다.** 아직 개념을 따로 공부해야 함.
> - 실제로 고치지는 못했으므로 마지막은 **FAIL 원인 분석 + 해결 방법**으로 마무리한다. ("고쳤다" ✗, "이렇게 고치면 된다" ✓)

## 대본

### ① 팀 구성 (10초)

> 저희 팀은 3명입니다. Alarm Clock은 셋이 각자 구현해서 가장 좋은 코드를 골랐고, 그다음 저는 Priority Scheduling을 맡았습니다.

### ② 구현 (12초)

> Alarm Clock은 전부 통과했고, Priority Scheduling도 대부분 통과했습니다. 오늘은 실패한 테스트 중 priority-sema를 같이 보려고 합니다.

### ③ 트러블슈팅 (72초)

**3-1 맛집 웨이팅으로 복습 (15초)**

> 원인을 찾다가 제가 세마포어를 제대로 모른다는 걸 알게 됐는데요, 다들 같은 문제를 푸셨으니 맛집 웨이팅으로 같이 복습해 보겠습니다. value는 빈 자리 수, waiters는 대기표를 받고 기다리는 손님 줄입니다.

**3-2 두 함수가 하는 일 (18초)**

> sema_down은 가게에 들어갈 때 부르는 함수입니다. 빈 자리가 있으면 바로 들어가고, 없으면 대기표를 받고 잠듭니다. sema_up은 다 먹고 나올 때 부르는 함수입니다. 자리를 하나 내놓고, 기다리는 손님이 있으면 호출합니다.

**3-3 헷갈리기 쉬운 점 (14초)**

> 저는 sema_down은 기다리는 스레드, sema_up은 깨워 주는 스레드처럼 역할로 생각해서 오래 막혔습니다. 사실 둘은 한 스레드가 들어갈 때와 나올 때 부르는 함수입니다. 자리가 있으면 sema_down을 불러도 기다리지 않습니다.

**3-4 FAIL 원인과 해결 방법 (25초)**

> 이제 원인이 보입니다. 지금 sema_up은 list_pop_front로 대기표 순서대로, 먼저 온 손님을 부릅니다. 테스트에서는 27이 먼저 대기표를 받고 30이 뒤에 받는데, 우선순위 스케줄링이라면 VIP인 30을 먼저 불러야 합니다. 그래서 고칠 점은 두 가지입니다. 첫째, 기다리는 스레드 중 우선순위가 가장 높은 스레드를 깨운다. 둘째, 깨운 스레드가 지금 스레드보다 높으면 바로 양보한다.

### ④ 회고 (20초)

> 공부는 그냥 재미있었습니다. 특히 계속 틀리던 이유를 파고들다가, 함수를 역할로 착각하고 있었다는 뿌리를 찾았을 때가 가장 재미있었습니다.
>
> 팀으로는 1주차와 달리 안정된 상태에서 차근차근 배울 수 있었고, 코드 리뷰를 하면서 잘하는 팀원이 문제를 어떻게 바라보는지 볼 수 있어 좋았습니다.
>
> 다음에는 무엇을 배울지, 또 얼마나 해낼 수 있을지 기대됩니다.

### 비유를 쓸 때 지킬 것

- 비유는 **맛집 웨이팅 하나**로 통일. 현실에서 쓰는 말만 쓴다: 빈 자리, 대기표, 호출, 들어간다/나온다.

  | 코드 | 맛집 웨이팅 |
  |---|---|
  | `value` | 빈 자리 수 |
  | `waiters` | 대기표 받고 기다리는 손님 줄 |
  | `sema_down` | 들어갈 때: 빈 자리 있으면 바로 입장, 없으면 대기표 받고 대기 (`thread_block`) |
  | `sema_up` | 나올 때: 자리 내놓고, 기다리는 손님 있으면 호출 (`thread_unblock`) |
  | `list_pop_front` | 대기표 순서대로 호출 |
  | 우선순위 | VIP |

- 화면에는 항상 **함수/필드 이름을 먼저**, 맛집 말은 옆에 붙인다. (예: `sema_down` — 들어갈 때)
- "직원"은 대본에 넣지 않음. 공부 노트에서 직원은 CPU를 뜻해서 섞이면 헷갈림. 호출은 "부릅니다"처럼 주어 없이 말한다.
- "VIP"는 3-4에서 처음 등장 → 우선순위를 맛집 말로 바꾼 것.
- 3-2 화면에 실제 코드 몇 줄을 같이 보여 주면 "아, 그 코드" 하고 바로 연결됨:
  - `sema_down`: `while (sema->value == 0) { list_push_back (&sema->waiters, ...); thread_block (); }` → `sema->value--;`
  - `sema_up`: `if (!list_empty (&sema->waiters)) thread_unblock (list_entry (list_pop_front (&sema->waiters), ...));` → `sema->value++;`
- 3-4 대기 줄 숫자는 실제 테스트 순서: main이 `PRI_MIN`으로 내려간 뒤 27, 26, 25, 24, 23, 22, 21, 30, 29, 28 순서로 스레드를 만들고, 각 스레드가 곧바로 `sema_down`에서 줄을 섬.
- 3-4는 **"고쳤다"가 아니라 "이렇게 고치면 된다"**로 말한다.
- condvar, `cond_signal`은 대본·슬라이드에 넣지 않는다.

### Q&A 대비

- **"가장 높은 스레드 깨우기"는 어떻게?** → 두 방법 중 하나. (가) `sema_up`에서 `list_max`로 가장 높은 스레드를 찾아 `list_remove` 후 깨우기 (나) `sema_down`에서 `list_insert_ordered`로 우선순위 순으로 줄 세우기. 단 (나)는 기다리는 동안 우선순위가 바뀌면(donation) 순서가 틀어지므로, `sema_up` 직전에 `list_sort`를 한 번 더 하는 경우가 많음.
- **"바로 양보"는 왜 필요?** → 테스트는 `Thread priority 30 woke up.`이 `Back in main thread.`보다 먼저 나와야 함. `thread_unblock`은 ready_list에 넣기만 하므로, `sema_up` 끝에서 깨운 스레드가 더 높으면 `thread_yield`를 해야 함.
- **priority-condvar는요?** → "condition variable은 아직 개념을 따로 공부해야 해서 이번 발표에서는 뺐습니다."
- **VIP가 이미 먹고 있는 손님을 쫓아낼 수 있나?** → 아니요. 우선순위는 READY 스레드 중 누가 CPU를 쓸지만 정함. 자리(자원)는 뺏지 못함.

## FAIL 원인 확인 (코드 기준, 실행은 못 함)

이 환경에 qemu가 없어 테스트를 직접 돌리지는 못했고, 코드와 테스트 기대 출력을 대조해 확인함. 발표에서는 "원인"으로 말해도 됨.

1. **V(`sema_up`)가 웨이팅 명단 맨 앞을 깨운다 → 확인됨**
   - `pintos/threads/synch.c:69` `sema_down`: `list_push_back`으로 명단 **뒤에** 추가 (온 순서대로 줄 섬)
   - `pintos/threads/synch.c:113` `sema_up`: `list_pop_front`로 명단 **맨 앞**을 깨움 (우선순위 무시)
   - `priority-sema` 테스트: main이 `PRI_MIN`으로 내려간 뒤 우선순위 27, 26, 25, 24, 23, 22, 21, 30, 29, 28 순서로 스레드를 만듦. 각 스레드가 바로 선점해 `sema_down`에서 줄을 서므로 명단 순서도 같음 → 현재 코드는 **27**을 먼저 깨우지만 기대 출력은 **30**부터.
2. **깨운 뒤 양보하지 않는다 → 함께 고쳐야 할 점**
   - 기대 출력은 `Thread priority 30 woke up.` 다음에 `Back in main thread.`가 나와야 함. 즉 깨어난 스레드(30)가 main(`PRI_MIN`)보다 먼저 실행돼야 함.
   - 지금 `thread_unblock`은 ready_list에 넣기만 하고, `sema_up`도 양보(`thread_yield`)를 하지 않음 → main이 계속 실행되어 `Back in main thread.`가 먼저 찍힘.
3. **condvar도 같은 원리 → 코드로 확인됨 (발표에서는 제외, 따로 공부 예정)**
   - `pintos/threads/synch.c:306` `cond_signal`도 `cond->waiters`에서 `list_pop_front`로 맨 앞을 깨움.
   - 차이: condvar의 명단 원소는 스레드가 아니라 `semaphore_elem`(각자 세마포어 하나씩)이라, 정렬할 때 "그 세마포어에서 기다리는 스레드의 우선순위"를 비교해야 함.
